# チケットから成果物まで — 試作版を引き取る入口

これは新しい役割チェーンの起動手順です。既存の本番サービスを更新する手順ではありません。
**バイナリがあること、モデルが完了と言ったこと、本番で依頼が完遂したことは別です。**
実モデル試験では納品と報告まで進んだ例も、複数モデルが誤記を承認した例もあります。翌朝の完成を保証できる状態ではありません。

## 配布物

- `bin/ticket-engine`: 受付、役割への引き渡し、実行履歴、再開。
- `bin/ticket-tracker`: 担当チケットの読取・コメント投稿。
- `harnesses/`: Git準備、既存Hermes SDKへの接続、Linuxの役割隔離。
- `examples/operator.json`: 実装、独立2者レビュー、納品、検証、報告の設定例。
- `RUNTIME.md`: SDK、隔離、ネットワーク、監督機能の前提と未検証事項。
- `README.md`: 設定詳細と実験記録。

判断はモデルに任せ、回答は普通の文章のまま次へ渡します。工程接続は、回答に印を付けて合格させる仕組みではありません。
この例はJevでモデルを選び、選んだLLMで次の担当と指示を決めます。作業とLLMによる担当選択の都度、現在のOpenRouter一覧を取得します。
対象publisherは `deepseek / minimax / moonshotai / qwen / z-ai`。作業モデルの版は固定しません。
Jevで直接担当を選ぶ比較は `router.mode` を `jev` にします。最適な方式が確定したという意味ではありません。
Jevの接続例は[OpenRouterのDecisions API](https://openrouter.ai/blog/insights/what-is-jev/)に合わせています。設定例のJevの版は選定役の指定です。

## 1. ビルド

ソースcheckoutの `rewrite/` で、存在しない出力先を指定します。

```sh
GOMAXPROCS=2 GOOS=linux GOARCH=arm64 sh package.sh /path/to/new-bundle
```

実行先がx86-64なら `GOARCH=amd64`。既存の出力先は上書きしません。Go 1.25以降が必要です。
SDKやコンテナimageはダウンロード・同梱しません。macOS用バイナリは作れますが、Linux役割ランチャーはmacOSでは動きません。

## 2. 実行環境と設定

先に `RUNTIME.md` を確認します。設定例は次の配置です。違う配置なら設定内の全該当箇所を変更してください。

| パス | 用意するもの |
| --- | --- |
| `/opt/ticket-automation/bundle` | この配布物。役割からは読取専用 |
| `/opt/hermes/bin/python` | SDKと依存関係を導入したPython |
| `/opt/hermes-src` | `run_agent` をimportできるSDKソース |
| `/etc/ticket-automation/operator.json` | 実設定。役割には公開しない |
| `/var/lib/ticket-automation/queue` | 再起動後にも残る履歴と作業場所。親ディレクトリを役割に公開しない |

`examples/operator.json` から実設定を作り、次を変更します。未編集の例は `project_id=0` と未設定の受付開始日時で受付を開始できません。

1. `backlog.base_url`: 接続先のAPI base URL。
2. `intake.project_id / created_since`: 任せるプロジェクトと受付開始日時（RFC3339、境界を含む）。既存チケットを不用意に取り込まない値にします。
3. 各processの `TASK_REPOSITORY`: 承認済みのソース。私有repoの認証は実行環境で準備します。再開時は既存の作業を上書きcloneしません。
4. `instructions`: プロジェクト知識の在り処、変更範囲、納品先、許可された納品コマンド、実物の検証方法、完了条件。設定例は納品権限やCIを用意しません。
5. 各processの `--write`: 許可する既存ディレクトリ。例は実装に `src / tests`、納品に `release`、報告作成に `report`。プロジェクトの構造に合わせます。

`--write .` はGit管理情報も含む作業場所全体の書込許可です。必要性と範囲を確認して選んでください。
レビュー・投稿・最終読返には書込許可を付けていません。project testを独立processとして加えるなら `model_env` を付けず、必要な権限だけ与えます。

資格情報はcontrollerの環境へ、既存の秘密管理経路から渡します。設定例が参照する**変数名**は `MODEL_API_KEY / TRACKER_API_KEY`。
値をJSON・コマンド引数・ログに書かないでください。作業役へは名指ししたモデル用の鍵だけを渡し、トラッカーの元の鍵は渡しません。本体が担当チケット限定のアクセスを発行します。
納品先の資格情報も、既存の `process.secrets` により必要な担当だけへ渡します。

**ネットワーク設定は省略できません。** `--network inherit` は親のネットワーク共有であり、宛先制限ではありません。
モデルAPIと担当チケット用の窓口への到達、および不要な管理API・他案件への接続拒否を実行環境で構成してください。
Docker診断で使った隔離緩和を、本番推奨設定としてコピーしないでください。

受付を有効にする前に、`RUNTIME.md` の「Check the target runtime before accepting work」を実行してください。
`bwrap` が置いてあっても、外側のcontainer設定が必要な隔離を拒むことがあります。鍵も依頼も渡さない確認です。

## 3. 限定した範囲で起動

設定・権限・接続を確認し、その範囲の実行が許可されてから起動します。

```sh
exec /opt/ticket-automation/bundle/bin/ticket-engine \
  --config /etc/ticket-automation/operator.json \
  --watch --run-dir /var/lib/ticket-automation/queue
```

既存の監督機能からcontrollerと子processの寿命を管理し、queueを永続化します。bundleはサービス登録・本番反映・再起動ポリシー設定をしません。
課題を1件受け付けたら、同じ課題の履歴、実際の納品先、保存された最終コメントを確認します。

工程は `要件詰め → (必要なら依頼者へ質問) → 調査 → 設計/実装 → 2者レビュー → 納品 → 実物検証 → 報告作成 → 2者報告レビュー → 投稿 → 読返`。
要件詰めは、依頼・checkout・運用者の指示から自分で決められることを決め、依頼者にしか決められない点だけを選択肢付きで残します。質問できるのはこの入口だけで、作業を任せた後は既存の担当で解決します。
指摘は修正へ、実行障害は復旧先へ渡します。回数だけで失敗完了にはしませんが、モデルの誤判断や恒久障害まで解決できる保証ではありません。

`examples/operator-stages.json` は同じ納品を別の形で書いたものです。`router.mode` を `stages` にすると、次に何をするかはモデルではなく、運用者が並べた工程と、その工程のコマンドが 0 で終わったかどうかで決まります。モデルが「できました」と書いても進みません。質問できるのは入口の 1 回だけで、最後の工程もコマンドです。コマンド自体は運用者が用意します。

## 4. 再開と停止

- 通常の再起動では同じ設定と**同じqueue**を使います。新しいqueueに替えると重複受付になり得ます。
- 中断した外部操作は「既に反映されたかもしれない」と次へ渡します。外部操作の厳密な1回実行を保証するものではありません。
- 元の起票者は、チケットへ最初の非空行が `停止` のコメントを投稿できます。追加の停止権者は `intake.stop_user_ids` に設定します。
- `intake.question_role` の担当が質問を投稿すると、その依頼はそこで待ちます。元の起票者 (または `intake.stop_user_ids`) がその質問より後にコメントすると、本文がそのまま履歴に入って再開します。`停止` の判定が先に走るので、停止は常に停止です。答えが来ない限り待ち続けます。
- 停止コメントを消しても自動では再開しません。履歴や停止記録を手で消して復旧させないでください。停止は外部操作の取消ではありません。
- `intake.stop_report_role` の専用担当が、停止とその時点の実測を同じチケットに報告します。この担当にclone準備、作業場所の書込権限、納品用の資格情報は渡しません。停止した元の依頼を成功扱いにせず、報告だけを別に再開できます。

## 引き渡し時に残すもの

「実装済み」「自動試験」「実モデル」「本番」の確認を分けてください。元の依頼、配布物、実行設定、納品先の実測、実際の最終コメント、未達事項を対応させます。
履歴は `queue/jobs/<課題ID>/run/history.json`、元の依頼は同じjobの `issue.json`。秘密や顧客情報を含み得る私有データなので公開repoへ貼りません。
