# チケットの書き方 — このエンジンに一発で受理されるために

対象読者: 人間の起票者と、起票を代行・支援する LLM エージェントの両方。ここに書いてあるのは書式の強制ではなく、**どう書けば質問往復や停止なしで実装まで流れるか**の実測に基づく指南。消費者 (インスタンス) 固有の値はインスタンス repo の同名ドキュメントにある。

## 大原則

1. **書式は自由。不足は拒否ではなく質問になる。** 取り込みは本文から契約を導出し、読み取れない点は選択肢付きの質問としてチケットのコメントに返す。ただし質問 1 往復 = 起票者の実時間なので、起票時に潰すほど速い。
2. **決めてあることは全部書く。** 着手可否の判定は「起票者にしか決められない曖昧さ」が残っていると質問を出し、検査役 (別ベンダーの敵対 AI) は「本文から導ける質問」を過剰として弾く。つまり**本文に明文がある事項は質問されない**。決定を焼き込んだチケットは判定を素通りする — これは実測で確認済みの性質。
3. **1 チケット = 1 つの納め物。** 変更量には予算 (行数・ファイル数・バイト数、インスタンス設定) がある。超えそうな依頼は分割して起票する。

## 質問が飛ぶ条件 (=起票時に自問するリスト)

判定役が質問してよいのは、次の 4 条件が全部成り立つ時だけ:
①複数の許される答えが利用者に見える結果を実質分岐させ ②本文・提供ソースから導けず ③その選択が結果を変え ④起票者にしか決められない。

だから起票前に、次の類型を自分で決めて本文に書く:

- **空・ゼロ・未設定の意味** (空リストは拒否か、解除と同義か、全禁止か — 実例: この 1 点の未定義で 1 枚が 2 回停止した)
- **既存データへの波及** (新ルールは既存の保存済み値に遡及するか。無変更の再保存は通すか)
- **境界の見え方** (拒否時に何が表示されるか。エラーか、黙って除外か)
- **範囲の境界** (どの画面/API までが対象で、どこからが対象外か)
- **一貫性 vs 変更量** (表示を全箇所で揃えるか、主要箇所だけか — 文章テンプレートの書き換えを含むか等)

## 受入条件の書き方

機械と人間の両方が判定できる観測可能な文で書く。「〜が API で拒否される」「〜が画面に表示される」の形。内部実装の言葉 (関数名・テーブル名) だけの受入条件は検証できない。

## 調査だけの依頼 — 変更なしで計って報告してほしいとき

「何が起きているか調べて」「〜の数を報告して」は調査の依頼。調査・設計役 (`docs/INVESTIGATING_DESIGNER.md`) が読み取り専用の probe で実物を計り、報告をチケットのコメントに掲示して `investigated` で終わる (PR は作られない。設計工程にも入らない)。実測で分かった、止まらずに流れる書き方:

- **1 行目に対象の納品先を書く** — 「対象: <納品先の名前> の本番」の形。稼働環境の言葉 (「本番コンソール」「3 つの入口」「全テナント」) だけでは、受付は本文からどの納品先 (repository) の話か決められない。その場合は質問を出さず、「運用担当者が確認する」と伝えて停止する (実例: 同じ内容の 2 枚がこれで止まり、冒頭に 1 行足して出し直すと受理された)。納品先の名前はインスタンス repo の同名ドキュメントにある。
- **数える範囲を、種類と扱いまで書く** — どの名前空間か、その中の**どの種類の Pod / 行を数えるのか、種類ごとに分けるのか合算か**。「全テナント」「全 Pod」だけだと、受付は「利用者用だけか、部署用や補助用も含めるか」を質問する。「名前空間内のすべての Pod」と書いても、納品先のコードに補助 Pod を飛ばす列挙規約があると「合算か別枠か」を質問される (実例)。「利用者用・部署用・補助用を区別せず、名前空間ごとに合算」のように扱いまで決めて書く。
- **「変更なし」を明記する** — 「コードや設定の変更はなし。読み取りで計って報告するだけ」。受入条件にも「変更提案や PR は作られていない」を入れる。
- **値の形を書く** — 「名前空間ごとに Pod 数 / READY でない数 / 再起動回数の合計」「件数だけでよい (本文や個人情報は不要)」のように、報告に載せる項目を並べる。報告は各値に実測の記録 ID を添え、生の出力はチケットの添付として付く。

## 走行中の作法

- 質問が来たら、選びたい選択肢の下の「回答 C1 Q1:a」形式の行を**そのまま 1 コメント**で貼る。自由文の回答は受理されない。
- 中止したければ「中止 C1」とだけコメントする。
- 採用された回答は knowledge に保存され、**同じ論点は次回から質問されない**。
- 終端 (納品 PR / 正直な停止) は必ずチケットにコメントで報告される。**同じチケットの再投入は不要** — 停止後の再走は運用者の仕事。

## 設計工程を省略したいとき — 「どう直すか」を本文に書く

受付は依頼ごとに「コードを書く前に設計 (実物を計ってから直し方を決める工程) が要るか」を判定し、結果と理由を受付後の【実装方針】コメントに 1 行で出す (「設計なし: 方針が本文にあるため設計を省略」/「設計あり: <理由>」)。既定は設計あり。次の 4 つが**全部**成り立つ小さな依頼だけ、設計を省略して実装に入る:

1. **本文に「どう直すか」が書いてある** — 「何がどう変わるべきか」だけでなく「どこを何に変えるか」まで。受付の起案役はその一文を本文からそのまま引用し、機械が本文に実在するかを照合する。言い換えでは通らない
2. **触るファイルが 2 つ以下** — 受付が本文から導出した対象ファイルの数。多い依頼は分割すれば減る
3. **稼働環境の観測を示す語が本文に無い** — 「遅い」「たまに」「本番で」「ログに」「原因」「調査」のような、そのインスタンスが設定した語彙 (インスタンス repo の設定 `design.trigger_words`)。これらがある依頼は、まず計ってから直し方を決める。語彙が未設定のインスタンスでは省略できない (安全側)
4. **依頼が「調査」ではない** — 「何が起きているか調べて」は調査の依頼で、設計工程の対象外 (設計なし)。調査の依頼は上の「調査だけの依頼」の節のとおり調査工程に入り、報告がチケットのコメントに掲示されて終わる (PR は作られない)

起案役と確認役 (別会社の AI 2 人) がそれぞれ判定し、片方でも「設計あり」なら設計ありになる。省略されなかった理由はコメントの同じ行に出るので、次の起票で潰せる。

## 書かなくてよいもの

- 実装手順の指定 (どのファイルをどう書くか) — 実装 AI が repo を読んで決める。書くなら「制約」として (例: 特定構文の禁止)。ただし上の節のとおり、「どう直すか」を書いておくと設計工程を省略できる — 書くかどうかは起票者の選択
- 変数名・コンポーネント構造・テストの書き方 — 質問対象外の実装裁量。
