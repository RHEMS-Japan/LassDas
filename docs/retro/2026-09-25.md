# Runner card and ticket binding

## User-visible failure and cause

A new ticket was processed in an older ticket's workspace. The new ticket's
own card failed to claim it and appeared stopped while another card was still
working on it. Claim recovery later returned the active ticket to the queue,
allowing a second implementation/review run. The terminal result and the
ticket's displayed stage history could therefore describe different attempts.

Why this happened:

1. The runner received a task id and workspace but did not resolve the task's
   delivery before pulling work.
2. Its `PullClaimRequest.RunID` was empty. The store correctly interpreted that
   as a request for the project's current pending ticket, not the card's ticket.
3. The pipeline kept the dispatched workspace even when the pulled delivery
   belonged to a different card; `Prepare` could clear that workspace's records.
4. Recovery used the canonical delivery-to-card mapping, so it consulted a
   failed card instead of the worker actually holding the claim.
5. Helper/store tests used explicit run ids, but no command-level regression
   asserted that the shipped runner supplied one or preserved a foreign history.

The reporting failure was separate: an earlier progress update reused an older
review status before refreshing the actual execution records. A board row alone
was not sufficient evidence while card and envelope identity disagreed. Runtime
diagnosis must compare the dispatched card, claimed envelope, and delivered PR,
and state when each was observed instead of implying an old observation is live.

## Repair and boundaries

The runner now resolves its existing card and ledger binding before claiming.
It checks the actual workspace from the canonical CLI and refuses an existing
envelope from another delivery (or one it cannot validate) before any cleanup or
terminal reporting. The existing exact-run Pull and owner CAS remain responsible
for claiming and duplicate-owner exclusion.

No new queue, state schema, mapping file, setting, consumer-specific rule, model
selection, retry budget, or card-recovery policy is introduced. Inferring the
delivery from a directory name was rejected: legacy scratch cards are valid,
and a later configuration change does not relocate an existing card's workspace.
Silently repairing already mixed histories was rejected because it would destroy
evidence and exceed the approved change. Live repair and deployment are separate.

## Regression checks

- Two queued deliveries with the pending slot pointing at the newer ticket:
  the older card must still claim only the older ticket, and the newer card must
  claim only the newer one. An attendant pass must preserve both live claims;
  another owner must not acquire an already claimed ticket.
- Missing/ambiguous cards, missing ledger bindings, wrong workspaces, cross-project
  same-named runs, invalid/linked/oversize envelopes, and unavailable Hermes:
  reject without claiming work or changing the recorded evidence.
- Same-delivery retries, genuine claim recovery, canonical directory aliases,
  and an existing workspace after a configured runs-root change remain usable.
- The built runner command must reject a foreign envelope, a different card, or
  a different workspace without altering history, current-step, spend, or envelope.
- An optional isolated-image test drives the installed Hermes CLI's create,
  claim, and list commands for persistent and scratch cards. No model, gateway,
  remote tracker, or production dispatcher is started.

Mutation checks must fail when command wiring bypasses binding, RunID is omitted,
foreign-envelope validation is removed, or workspace matching is disabled. The
command-level mutation reproduces both the wrong claim and history erasure;
testing only the new helper would miss this regression.
