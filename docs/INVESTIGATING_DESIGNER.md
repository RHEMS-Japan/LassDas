# 調査・設計役 — 実物を計ってから、直し方を決める係 (設計書 v0.1、issue #18)

発注者決定 (2026-09-04): **調査と設計は 1 つの役にする。実装は別の軽い役にする。**
理由は一文で言える — 動いているシステムの不具合や改修では、コードを読むだけの調査は推測であって実測ではなく、推測の上に建てた設計は実装役に忠実に間違えさせる。だから「計る」と「決める」は同じ頭で連続して行い、「写す」だけを分離する。

本書は #18 の受入条件 6 点を決める。実装はしない。用語は [TRUST_MODEL.md](TRUST_MODEL.md) に従う (指紋 = SHA-256、確定記録 = 自分の指紋を含む JSON)。

## 0. この係が要る根拠 (実測)

| 起きたこと | 何が足りなかったか |
|---|---|
| 「ログインを押してから遅い」型の依頼が、実装役の推測で 5 回失敗した | どの工程が遅いかを計る手段が実装役に無い |
| 調査型の依頼で実装役が手数上限 (1,000 手) を検索だけで使い切った | 「調べる」と「直す」を同じループでやらせた |
| 画面確認の不合格が「ログイン切れ」と診断された。実物を動かすと、ブラウザが起動していない・英語画面・写真の形式、と別の 3 つが先に出た | 設定とコードを読んだだけの診断は、もっともらしいが実測ではない |
| うまくいった判断 (ログインの取り直し・デプロイ直後の旧画面・写真の形式) は全部「実機で 1 回試して確定 → 直す」の順だった | 計ってから決める、を役として持っていない |

## 1. 一枚の絵

```
いま:  受付 (何を・どこを) ─→ 実装役 (どう直すかを考えながら書く) ─→ レビュー 2 名 ─→ 検証 ─→ 納品
                                     ↑ 方針の誤りはコードが出た後に見つかる (一番高い工程で差し戻し)

これから:
  受付 (何を・どこを・設計が要るか)
    │
    ├─ 設計不要 (方針が本文にある小さな変更) ──────────────────────────→ 実装役 (従来どおり)
    │
    └─ 調査・設計役 (リポジトリ + 稼働環境を読み取り専用で計る)
          │  出力 1: 調査報告 (実測の一覧つき)      ← 調べるだけの依頼はここで終わり
          │  出力 2: 設計書 (原因・方針・触るファイル・変更内容・確認方法)
          ▼
       レビュー 2 名が設計書を判定 (コードを書く前に方針を止められる)
          ▼
       実装役 (軽いモデル): 設計書を写す。判断しない
          ▼
       レビュー 2 名: 「設計書どおりか」だけを見る ─→ 検証 ─→ 納品 (以後は従来どおり)
```

関所 (AI ではない Go プログラム) は、調査報告と設計書も確定記録にし、実装役の指示・実装後のレビュー・納品ゲートを設計書の指紋で束縛する。信用するのは関所だけ、という原則はそのまま。

## 2. 登場人物に 1 行足す

| 登場人物 | 正体 | 役目 | 信用するか |
|---|---|---|---|
| **調査・設計役** | AI 1 人 (重いモデル) | 稼働環境とリポジトリを読み取り専用で計り、調査報告または設計書を書く。**書き込みはできない** | **しない** |

実装役は「軽いモデル・少ない手数・判断しない」に変わる (設計書つきの依頼のとき)。レビュー役 A/B は設計書と実装の 2 回判定する。

## 3. AC1 — 道具と、機械の縛り

### 道具 (何を計れるか)

道具は「消費側が設定で宣言した実測の形」だけ。フレームワークは形を所有しない (消費側の事情は設定として外から受け取る)。

```json
"probes": [
  {"id": "pods",     "argv": ["kubectl", "--context", "<ctx>", "-n", "<ns>", "get",  "pods", "-o", "wide"]},
  {"id": "logs",     "argv": ["kubectl", "--context", "<ctx>", "-n", "<ns>", "logs", "{{pod}}", "--since", "{{since}}"], "args": {"pod": "^[a-z0-9-]+$", "since": "^[0-9]+[smh]$"}},
  {"id": "aws",      "argv": ["aws", "--profile", "<readonly>", "{{service}}", "{{verb}}"], "args": {"service": "^[a-z0-9-]+$", "verb": "^(describe|get|list)-[a-z-]+$"}},
  {"id": "sql",      "argv": ["psql", "<readonly dsn>", "-v", "ON_ERROR_STOP=1", "-c", "{{query}}"], "args": {"query": "^\\s*(SELECT|EXPLAIN)\\b"}},
  {"id": "http",     "argv": ["curl", "-sS", "-o", "/dev/null", "-w", "%{http_code} %{time_total}", "--max-time", "20", "{{url}}"], "args": {"url": "^https://<allowed hosts>/"}}
]
```

- 各 probe は **固定の argv + 正規表現で形を縛った穴** だけ。役は穴に値を入れることしかできない。シェルは渡さない (パイプ・リダイレクト・変数展開が無い)
- 出力の上限 (既定 256 KiB) と時間の上限 (既定 60 秒) を probe ごとに持つ
- 役はリポジトリ (納品先の作業コピー) を読める。書き込みはできない (読み取り専用マウント)

### 縛り (3 層、本体は 1 層目)

1. **資格情報が書けない** — これが本体。AWS は読み取り専用ロール (describe/get/list のみの管理ポリシー)、DB は読み取り専用ユーザー (`default_transaction_read_only = on`、対象スキーマの SELECT のみ)、Kubernetes は get/list/watch のみの ServiceAccount。**役がどんなコマンドを組み立てても、鍵が書けなければ書けない。**
2. **コマンドの形の関所** — LassDas の実測ラッパー (`probe` 副命令) がカタログ外の argv・正規表現に合わない穴を **実行前に拒否して記録する**。Hermes 側も `approvals.single_query_mode: deny` (無人実行で承認が要る命令は自動拒否) と `approvals.deny` (書き込み動詞の globs) を重ねる。ここは費用と早期停止のためで、保証の根拠ではない
3. **実行環境** — 作業ディレクトリは実測の記録だけを書ける場所。納品先リポジトリは読み取り専用。ネットワークは probe の許可ホストだけ (egress の制限は消費側の基盤に任せる)

**プロンプトは縛りではない。**「書き込みをしないでください」は書くが、それを守ったから安全なのではない。

### 記録 (何を計ったかが後から追えること)

実測は 1 件ごとに `{probe id, 埋めた値, 開始/終了時刻, 終了コード, 出力本文 (上限内), 出力の指紋, 使った資格情報の名前}` を関所が書く。役が要約したものではなく、ラッパーが取った生の出力。

## 4. AC2 — 出力の形式

### 調査報告 `investigation.json` (確定記録)

| 項目 | 中身 |
|---|---|
| `questions` | 何を確かめようとしたか (依頼から役が立てた問い、最大 8) |
| `measurements[]` | 上記「記録」の一覧。役が引用するのは **ID だけ** |
| `findings[]` | 分かったこと。各項目は `{claim, evidence: [measurement ids], confidence: measured / inferred}`。**`measured` は引用した実測が無いと関所が拒否する** |
| `unknowns[]` | 計れなかったこと・計らなかったこと (「不明は不明と言う」) |
| `next` | 次の一手 (調査だけの依頼ならここで終わり) |

### 設計書 `design.json` + `DESIGN.md` (確定記録 + 人が読む写し)

| 項目 | 中身 | 関所の検算 |
|---|---|---|
| `cause` | 原因の一文と、根拠の実測 ID | 実測 ID が存在し、`measured` を最低 1 件含む (推測だけの原因は不成立) |
| `approach` | 方針の一文と、採らなかった案 (1〜3) | — |
| `files[]` | 触るファイルと、各ファイルで何をどう変えるか (箇条書き) | 全部が消費側の許可範囲 (`allowed_file_prefixes`) の中。数と行数の見込みが上限内 |
| `verification` | 確認する画面・出ているべき表示・消えているべき表示 | 3 条件: 出ているべき表示は変更前の対象ファイルに無い / 変更後にある見込み / 画面に見える見込み。前者 2 つは受付と同じ検査、3 つ目は写真係が最終判定 |
| `blast_radius` | 影響する画面・機能・利用者 | — |
| `not_doing` | やらないこと (依頼の外) | — |
| `evidence` | 引用した実測 ID の一覧 | `investigation.json` の指紋に束縛 |

チケットに見せるもの: 「調査報告」コメント (findings の要点 + unknowns + 実測の生出力を添付) と、従来の「実装方針」コメントの中身を設計書の要約 (cause / approach / files / verification) に置き換える。**頼んだ人は、コードが書かれる前に方針を読める**。

## 5. AC3 — 設計レビュー (コードの前に方針を止める)

- レビュー役 A/B (別会社) が `design.json` を判定する。判定の形は既存と同じ (`verdict: pass | revise`, `findings[]`)。1 人でも revise なら不成立で、調査・設計役がやり直す
- 観点 (lens) は実装レビューと分ける:
  - **A (根拠)**: 原因は実測に支えられているか。`inferred` だけで立っている結論はないか。計るべきで計っていないものはないか
  - **B (方針)**: 触るファイルは必要十分か。副作用の見落としは。確認方法は本当にその変更を判定できるか (3 条件)。より小さい直し方はないか
- 巡数は設計専用の上限 (`chain.design_max_rounds`、既定 3)。上限でも合意しなければ **正直に停止** (既存の「質問 2 回」経路に載せる: 争点を発注者に 2 択で聞く)
- 設計レビューの合格 = `design.json` の指紋が確定し、以後の実装役の指示・実装後レビュー・納品ゲートがその指紋を参照する。設計書の改変は関所が検出する

## 6. AC4 — 設計を飛ばす条件 (受付が決める)

受付 (起案役 + 別会社の確認役) の出力に `needs_design: bool` と理由を足す。既定は **「設計あり」**。飛ばすのは次を全部満たすときだけ:

1. 依頼本文に「どう直すか」が書いてある (対象ファイルと変更内容が読み取れる)
2. 対象ファイルが 2 つ以下で、変更行の見込みが消費側の上限の 1 割以下
3. 稼働環境の観測を示唆する語が無い (「遅い」「たまに」「本番で」「ログに」など)
4. 依頼者が「調査」「原因」を求めていない

判定は確認役が検算する (受付と同じ機械矯正: 起案役が飛ばすと言い、確認役が反対なら設計あり)。理由はチケットの受付コメントに 1 行で出す (「方針が本文にあるため設計を省略」)。

## 7. AC5 — 実装役の契約 (設計書つきの依頼)

- **指示** = 設計書 (`DESIGN.md` 全文) + 守ること。「設計書に書かれていない変更をしない」「設計書の `files[]` 以外を触らない (許可範囲をさらに狭める)」「迷ったら止まる」
- **迷ったら止まる** の形: 実装役は `revise-design` という終端を返せる (理由つき)。関所はそれを設計レビューの差し戻しと同じ扱いにして、調査・設計役に戻す。実装役は質問しない・自分で決めない
- **モデルと手数**: 設計書つきの依頼は `agents.applier` (軽いモデル、手数上限 40、壁 20 分) で動かす。設計なしの依頼は従来の `agents.implementer`。どちらも設定
- **実装後のレビュー**: lens を「設計書どおりか」に切り替える (差分の各ファイルが `files[]` の記述に対応しているか、余計な変更がないか、確認方法が満たされる見込みか)。方針の再審はしない (設計レビューで済んでいる)

## 8. AC6 — 本番データの境界 (発注者が決める)

環境ごとに「読んでよいもの」を資格情報で分ける。プロンプトで分けない。

| 環境 | 状態・ログ・設定・計測 | 保存されたデータ | 秘密 |
|---|---|---|---|
| ステージング | 可 | 可 | 不可 |
| 本番 | 可 (ログは本文を含むものを除く) | **原則不可** (顧客の会話本文・個人情報を含む行)。集計と件数は可 | 不可 |

実現の形 (案):

- 本番の DB ユーザーは、顧客コンテンツを持つ列にアクセスできないビュー/スキーマにだけ SELECT を許す (列単位の GRANT)
- 本番のログは、本文を含むログ種別を probe カタログから外す
- モデルへの実送信本文 (保管されていれば) は本番では読まない
- 秘密 (鍵・トークン・cookie) はどの環境でも読まない。probe の出力に鍵の形が出たらラッパーが伏せる (既存のガードレールに委ねる)

**決めてもらうこと**: 上の表でよいか。特に「本番の保存データは原則不可」を、調査に必要な最小限 (件数・時刻・ID の存在確認) まで緩めるか。

## 9. 段階導入

| 段階 | 内容 | 受入 |
|---|---|---|
| 0 | 資格情報 3 本 (AWS 読み取りロール / DB 読み取りユーザー / K8s 読み取り SA) と probe カタログ。**中身を提示してから適用** | 書き込みを試みると鍵で拒否される (故意の試験を残す) |
| 1 | 調査モードだけ (設計書は書かない)。調べるだけの依頼を 1 本流す (例: ログイン後の遅延を工程ごとに計る) | 調査報告がチケットに付き、findings の全 `measured` が実測 ID を引用している |
| 2 | 設計モード + 設計レビュー + 軽い実装役。無害な変更依頼を 1 本流す | 設計書がレビューを通り、実装役が設計書どおりに写し、写真つき合格まで届く |
| 3 | 設計を飛ばす判定を有効化 | 小さな依頼が設計なしで通り、理由が受付コメントに出る |

段階 0 の前に、`probe` ラッパーと `investigation.json` の関所は単体テストで先に固定する (稼働環境なしで検査できる部分は全部そうする)。

## 10. 回帰セット (RUNTIME_POD.md の表に足す行)

| 死因 | 固定するテスト |
|---|---|
| カタログ外の argv、正規表現に合わない穴、シェルの断片 (`;` `|` `$(`) が実行される | probe ラッパー: 拒否して記録、実行しない |
| `measured` の finding が実測 ID を引用していない / 引用先の指紋が transcript と違う | investigation の関所 |
| 設計書の `files[]` に許可範囲外のパス / 確認方法が 3 条件を破る | design の関所 |
| 実装役が設計書に無いファイルを変えた | 実装後レビューの機械検査 (差分 vs `files[]`) |
| 設計レビューが上限巡で合意しないまま実装に進む | 設計巡の終端 |
| 受付が「設計不要」と言ったが確認役が反対 | needs_design の機械矯正 |
