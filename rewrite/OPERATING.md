# 質問への回答・編集・代理回答

対象は `--watch` の受付です。Backlog と GitHub Issues で、回答の選び方は同じです。
これは現在の実装をローカルの実プロセスとトラッカーの代役で測った手順で、実サービスや実モデルでの受入記録ではありません。

## 依頼者がすること

質問の選択肢への答えは、**質問の後に新しいコメントを 1 件**投稿してください。
複数の点を聞かれていたら、同じコメントにまとめます。過去のコメントの編集だけでは新しい回答になりません。
鍵の値はコメントに書かず、必要な権限・接続の準備を運用者に頼みます。

| 操作 | 本体がすること |
| --- | --- |
| 質問より古いコメントを編集する | コメント番号が質問以前なら、回答として取り込まない |
| 質問後のコメントを、取り込まれる前に編集する | 次の読取で返った時点の本文を取り込む。編集履歴から前の本文を復元しない |
| 同じ読取の時点で、回答コメントが 2 件以上ある | 権限がある人の最初の非空コメント 1 件だけを回答にする。連結しない |
| 取り込まれた回答を後から編集する | 保存済みの回答履歴を差し替えず、自動でやり直さない |
| 取り込み後や完了後に追加コメントを投稿する | それだけで回答履歴に追記したり、完了した依頼を起動し直したりしない |
| 本文が空・空白だけ、または本文の無い状態変更 | 回答にしない |
| 他の人が「依頼者の代理です」と書く | 文中の名乗りでは許可しない。実際の投稿者のアカウント番号で判断する |

「取り込まれた」は画面の回答履歴で確認できます。`intake.announce` を有効にしていれば、質問ごとに回答受領の通知も出ます。続けて別の質問に答えた場合も、30 分待つ必要はありません。同じ回答の再読取では重複通知しません。
読み取りと編集が同時に起きた場合、どちらの本文を本体が読めたかで決まります。投稿直後の編集に依存せず、最初からまとまった回答を出してください。

履歴に自動追記されないことと、後の役がそのコメントを読めないことは別です。
課題読取権限を持つ役がコメント一覧を読み直せば、追加・編集後の文面を参照する可能性があります。
訂正を確実に優先させたいときは、進行中の仕事への影響を運用者と確認してください。
止める必要があれば下の停止を使い、訂正後の内容で新しい依頼を出します。単にコメントを足して「反映された」とは扱わないでください。

## 代理で答える運用者

回答できるのは元の起票者か、`intake.stop_user_ids` に明示されたアカウントです。
この設定は回答専用ではなく、停止の権限も与えます。表示名やログイン名ではなく、トラッカーが返す数値のアカウント番号を使います。
代理回答が先に読まれれば、それが回答になります。後から来た起票者の答えで自動的に置き換えません。

本体自身の受付・開始などの通知は、その保存されたコメント番号で回答候補から除外します。
質問役の実際の投稿番号より後の回答を読みます。本文の書式や「正解か」は機械で検査せず、次の役へ原文を渡します。
質問が複数のコメントに分かれた場合の境界は、質問役が最後に保存した投稿番号です。質問役には 1 件にまとめて投稿させてください。

## 止めるとき

起票者か上記の運用者が、最初の空白でない行を正確に `停止` としてコメントします。
2 行目以降に理由を書いても構いません。同じ行に理由を足すと停止指示にはなりません。停止は回答より先に調べるので、回答待ちでも停止になります。
`> 停止` という引用、説明の 2 行目の `停止`、`停止しないでください` は停止指示ではありません。

停止は、既に外部へ出た変更の取り消しではありません。保存済みの停止指示はコメントを削除・編集しても解除されません。
履歴や停止記録を手で消して続けないでください。再開方法の確認と、既に納品されたものの確認が必要です。
GitHub issue を閉じたり受付ラベルを外したりするだけでも、受付済みの仕事は止まりません。

## 待つ時間と設定

質問の回答期限は現在ありません。答えがない間は待ち続け、停止指示があれば止まります。
通常の再起動では同じ queue を使い、既存の質問と回答を保持します。回答だけで、ファイル・納品・鍵の権限が広がることはありません。

質問できる場所は workflow の設定で決まります。出荷する順次工程の例では、初回だけでなく検査・レビュー・納品の失敗後に要件確認へ戻り、必要なら質問します。
別の接続や `on_failure` を使う設定では、その設定の経路に従います。詳しい設定は [README.md](README.md)、起動は [START.md](START.md) を参照してください。

## 確認した試験と限界

`cmd/engine/comment_operations_test.go` は、両トラッカーの native metadata で編集・分割・代理回答を確認します。
実 collector の試験では、質問投稿→回答前の再起動→編集済み本文と複数回答の読取→履歴への保存→完了後の編集・追加→再起動を通します。
既存の質問・停止試験と合わせたもので、実トラッカーの編集反映の遅延、モデルが回答をどう理解するか、代理回答の組織上の妥当性までは確かめていません。
