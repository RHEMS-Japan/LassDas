# initで決める事項の一覧

更新: 2026-09-14。全体方針: [PRODUCT_DIRECTION.md](PRODUCT_DIRECTION.md)。議論の入口: [issue #160](https://github.com/RHEMS-Japan/LassDas/issues/160)。

導入の準備から、合意・保存・起動・試験・通常利用・変更・終了までを見直した、現時点の設計台帳。**12領域・90項目**を、具体的な場面、必要な設計・実装、受入で確かめることへ対応付ける。さらに、組み合わせたときの抜けを30場面で点検する。

これは全項目への対応を初期実装に約束する一覧でも、利用者へ順番に尋ねる質問票でもない。既存の指示・設定・道具で足りる項目はそれを使う。新しい機構の必要性と、初期に扱う範囲は分けて判断する。将来の全ワークフローを列挙せず、導入に必要な決定の観点を揃える。

## どこで何を決めるか

LassDas側では、初期に提供する範囲、役の責務、必須レビューとゲート、未対応時の振る舞いを決める。導入先では、その範囲の中で以下を具体化する。initは先に調べ、推奨できる通常の選択を示し、利用者の目的・許可・制約が必要な部分だけを聞く。該当しない項目は理由を残す。

| 導入先で具体化すること | 内容 | 関連項目 |
|---|---|---|
| 対象と知識 | 対象repo・作業範囲・既存手順の参照先。複数アプリがある場合は今回任せる対象。 | A03・A05・B01・B02 |
| 作業と納品 | 作業の起点・PR先・マージ可否と条件・担当が完了する地点。 | E01〜E09 |
| 検証 | 何を、どの状態で、どう検証し、何を根拠に合格とするか。依頼固有のテストは実行時に具体化。 | C07・F01〜F08 |
| 受付と会話 | 課題管理の接続先・受付対象・開始時点・有効な回答や承認・処理順・元チケットの扱い。 | D01〜D08・I03 |
| 実行と接続 | 稼働場所・使える道具・接続先のアカウントと権限・秘密への参照。 | A04・G01〜G08 |
| 役割と制約 | 各役のモデルと鍵への参照・情報取扱い・費用と時間の上限・代替モデルの許可。 | H01〜H07 |
| 人の判断と例外 | 人に戻す条件・必要な確認材料・待機期限・停止や再開の操作。特定の個人への固定を必須にしない。 | B06・F07・J03〜J08 |
| 共有と変更 | 共有する合意・個人の進捗・記録の保存先と公開範囲・変更の適用・終了時に残すもの。 | C01〜C08・K01〜K06 |
| 初回の実証 | 小さな試験依頼・通す経路・確認済みの範囲・残る未検証部分。 | I01〜I06・L01 |

各依頼の目的・個別のテスト・受入条件は実行時に具体化する。initで将来の全依頼を決めず、本体の必須条件も各利用者へ選び直させない。

## 決定から実装・受入への引き継ぎ

1. 議論した項目IDに、決定・理由・見送った案とissueの参照を追記する。既に合意した原則は聞き直さない。
2. 決定後、後続の設計・実装欄を実際に必要な差分へ絞る。既存の指示・設定・道具で満たせる場合は、その根拠を残す。
3. 実装に着手する範囲を別途定め、該当する項目ID・受入条件・実装issueを結び付ける。新しい状態管理や共通基盤を一覧から自動的に起こさない。
4. 採用した経路を実際に確かめ、成果物・確認した対象・結果の参照を残す。未検証と対象外を区別する。
5. 試験で見つけた新しい論点は、該当項目へ追記するか、既存IDを変えずに追加する。

現行本体との既知の差は、[#167の読取り調査](https://github.com/RHEMS-Japan/LassDas/issues/167#issuecomment-5646927338)で追う。PR先・検証・マージ・完了の接続は[ToBeと受入の対応表](https://github.com/RHEMS-Japan/LassDas/issues/167#issuecomment-5646952369)、実行役によるテスト作成は[決定記録](https://github.com/RHEMS-Japan/LassDas/issues/167#issuecomment-5647009028)も参照する。

この一覧の作成では、停止中の実装・導入試験・運転を再開しない。設計レビュー、残る製品判断、実装の切り分け、実装後の実地受入は別の残作業として追う。
