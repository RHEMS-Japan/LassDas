# 実測手順書

**前提**: 受付基盤の有効化（インスタンス側の手順書）が完了し、受信が有効になっていること。

**目的**: チケット 2 枚を通し、結果を台帳に残す。

> **この 2 枚が証明するのは配管であり、製品ではない。** 詳細は README「正直な限定」。

---

## 起票の書き方

起票者が書くのは **5 行のヘッダと本文**だけ。**どのファイルを直すかは書かない。** 変更前の文言から自動で特定される。

```
Automation-Run-ID: <repo 変数 BACKLOG_AUTOMATION_RUN_ID の値>
Automation-Mode: client-visible-change
Verification-Path: <変更が見える画面のパス>
Expected-Text: <変更後の文言>
Absent-Text: <変更前の文言>
---
<普通の日本語で依頼を書く>
```

**書式の決まりごと**（機械検証済み）:

- ヘッダはこの順序。`Automation-Run-ID` と `Automation-Mode` は固定値
- `Expected-Text` と `Absent-Text` は 8 バイト以上 512 バイト以下で、互いに異なること
- 区切りは `---` だけの行
- 本文は 16KB まで
- **本文の前後の空行・末尾の改行は問題ない**（正規化される）
- `Target-File:` を書くこともできる。書けば範囲がそこに絞られ、書かなければ `Absent-Text` の文言を含むファイルが対象になる

**貼る前に検査できる。** 本文をファイルに保存して次を実行すると、受け付けられるか、何を読み取ったかが分かる。

```bash
go run ./cmd/worker check-ticket \
  --config config/m1-consumer.json \
  --run-id "<受付番号>" \
  --description <本文を保存したファイル>
```

**`Absent-Text` の選び方が結果を決める。** これは「変更後には画面から消えているはずの文言」であり、対象ファイルの検索キーでもある。

- 画面に実在する文言をそのまま使う
- 短すぎると無関係な箇所に当たる。8 バイト以上を必須にしているのはこのため
- 変更を許可された範囲 (`client/src/`) の中に無ければ、処理は「変更対象の文言が見つからない」として停止する
- 許可範囲内の 3 ファイル以上に出現すると、「どれを指すか判断できない」として停止する（1 回に変更してよいのは 2 ファイルまで）

## Ticket A: 正常系

**狙い**: 質問ゼロで本番確認まで到達すること。明確な依頼に質問しない（false-block でない）ことの実測を兼ねる。

**選ぶ変更**: `client/src/` 配下の 1 ファイルにだけ現れる文言で、画面上で目視確認できるもの。

```
Automation-Run-ID: <受付番号>
Automation-Mode: client-visible-change
Verification-Path: /settings
Expected-Text: 通知設定
Absent-Text: お知らせ設定
---
設定画面の「お知らせ設定」という見出しですが、通知のオンオフを設定する場所なので
「通知設定」の方が伝わると思います。変更をお願いできますか。
```

**観測すること**:

| いつ | 見る場所 | 期待 |
|---|---|---|
| 起票から 10 分以内 | チケットのコメント | 受付コメント。7 項目（状態・次に行動する人・操作・次回通知/期限・本番の状態・自動再試行・識別子）が揃う |
| 処理中 | チケットのコメント | 中間コメントは出ない（受付後は最終結果まで無言が正しい） |
| 完了時 | チケットのコメント | 最終結果コメント。本番の状態が「確認済み」、証拠 URL が載る |
| 完了後 | `Verification-Path` の画面 | 新しい文言が表示され、古い文言が消えている |

## Ticket B: clarification 経路

**狙い**: 質問 → 回答 → 再開 → 本番確認まで到達し、**選んだ回答が本番の結果に実際に反映されている**こと。

**選ぶ変更**: 同じ文言が画面上の 2 箇所（見出しとボタンなど）にあり、どちらを変えるかで見え方が変わるもの。依頼文では**どちらとは書かない**。

```
Automation-Run-ID: <受付番号>
Automation-Mode: client-visible-change
Verification-Path: /settings
Expected-Text: 通知設定
Absent-Text: お知らせ設定
---
「お知らせ設定」という表記を「通知設定」に変更してください。
```

**観測すること**:

| いつ | 見る場所 | 期待 |
|---|---|---|
| 質問時 | チケットのコメント | 選択肢付きの質問。各選択肢の下に「回答 C1 Q1:a」のような貼り付け用の行がある |
| 回答 | チケットにコメント | 貼り付け用の行を**そのまま 1 行貼るだけ**で回答できる |
| 回答から 10 分以内 | チケットのコメント | 受領コメント。どのコメントの回答を採用したかが書かれている |
| 完了時 | `Verification-Path` の画面 | **選んだ方だけ**が変わっている（両方選んだなら両方） |

**回答の書式**（機械検証済み）:

- 質問コメントの貼り付け用の行をそのまま投稿する
- 全角コロン・全角空白・小文字・スペース欠け・行の順序違いは救済される
- 読み取れなければ書式案内が 1 回だけ返る
- 回答が足りなければ、足りない質問だけが再掲される
- 中止するときは先頭行に `中止 C1`（一言添えても中止として扱われる）

## 記録すること

各チケットについて、以下を `docs/e2e-evidence/m1-measurement/<ticket-a|ticket-b>/` に残す。

- 受付コメント / 質問コメント / 受領コメント / 最終結果コメントのスクリーンショット（URL バーを含むウィンドウ全体）と時刻
- 変更後の画面のスクリーンショット
- 起票から最終結果までの所要時間
- 何段目の生成で収束したか（実行履歴から）
- レビュー 2 系統がそれぞれ何を指摘したか

最後の 2 つは #9 に併走させる調査項目。**判定者 2 体のうち 1 体は生成モデルと同一モデル**であり、異種ベンダーの敵対レビューという設計の中核仮説が実際に成立しているかを、この記録で初めて確かめられる。

## 通らなかったとき

**再起票しない。** 同じ受付番号は 1 回しか使えず、2 枚目以降は無視される。

停止した場合は最終結果コメントに停止地点と理由が載る。よくある原因:

| コメントの内容 | 意味 | 対処 |
|---|---|---|
| 入力が許可された形式または範囲に一致しなかった | ヘッダの順序・必須項目・文言の長さのいずれか | 上の「書式の決まりごと」と照合する |
| 対象リポジトリと本番環境は変更していません（受付条件） | 着手可否の判定が通らなかった | 判定の記録を実行履歴で確認する |
| 確認事項への回答が期限までに得られなかった | 回答待ちのまま期限切れ | 短縮タイマーで再現して原因を切り分ける |
