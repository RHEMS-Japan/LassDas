# 現在地と引き継ぎ

このファイルは「いま何が入っていて、何が残っていて、次に触る人が最初に何を確かめるか」だけを書く。契約そのもの（何がどう動くか、設定と既定）は [README.md](../README.md) の「いまの契約（実装済みの動き）」が正本で、ここでは繰り返さない。

最終更新: 2026-09-26。

## 1. 設計はどこにあるか

**無人完遂の設計そのものは、この repo の外の計画文書として書かれた。** 恒久的に残るのは次の 3 つで、設計を読み直したいときはこの順に読む。

1. **[README.md](../README.md) の「いまの契約」** — いま動いているものの正本。巡・停滞の裁定・はしご・質問・Go・終端条件と、その設定と既定
2. **各変更の commit** — 1 コミット 1 文の主語のある文で、なぜそう変えたかが本文に入っている。下の 12 本がその単位
3. **コード内のコメント** — この repo は「なぜそうなっているか」をコードの隣に置く方針で書かれている。`internal/attendant/ladder.go`、`internal/attendant/stagnation.go`、`internal/attendant/depth.go`、`internal/runner/reception_record.go`、`internal/hook/report_service.go` の先頭コメントは、それぞれの機構の設計文書そのもの

領域ごとの文書は `docs/` にある。導入は [SETUP.md](SETUP.md)、依頼を出す人向けは [OPERATING.md](OPERATING.md) と [TICKET_AUTHORING.md](TICKET_AUTHORING.md)、製品の方向は [PRODUCT_DIRECTION.md](PRODUCT_DIRECTION.md)、設計役の仕様は [INVESTIGATING_DESIGNER.md](INVESTIGATING_DESIGNER.md)。

## 2. 無人完遂の中身 — 12 本の変更

「受付を通った依頼は、人に何も聞かず、失敗しても止まらず、必ず最終コメントで終わる」を成り立たせるために入れた変更。上から順に積まれている。

| # | 変更 | 何が変わったか | 効く設定 |
|---|---|---|---|
| 1 | 工程の失敗記録 | 失敗したカードが「何の失敗か」(`model` / `network` / `tool` / `validation` / `disk` / `credit` / `unknown`) を自分で書き残す。以降すべての土台 | なし |
| 2 | 検証の失敗を次の巡へ | 検証が落ちた巡を終端にせず、落ちた出力を次の巡の指示に載せる。どのコマンドが落ちたかを記録の末尾に残す | なし |
| 3 | 解決のはしご | 失敗したカードを報告せずに登る。まだ試していない手を 1 つ打って配り直し、同じ手は二度打たない。手が尽きたら倍々の間隔で待つ | `chain.retry_backoff_base_seconds` / `chain.retry_backoff_max_seconds` / `chain.retry_max_attempts` / `chain.retry_notice_attempts` |
| 4 | 役ごとの候補座席 | 答えないモデルを別の提供元の別モデルへ移す。読めないレビューはその座席の失敗として扱う。設計の判定役 2 人も提供元を分ける | `models.<役>.candidates` / `agents.<役>.candidates` |
| 5 | 停滞の裁定 | 直前の巡と指摘・変更が完全一致した場合に加え、消えた同じ指摘や以前の不合格と同じ変更へ戻る往復も、本体が受入条件を読んで裁定する。依頼者には聞かず、合格条件や変更範囲も緩めない | `max_rounds` / `stagnation_repeat_rounds` / `models.arbiter` |
| 6 | 実装役を戻さない | 実装役が「変更せずに理由だけ返す」形で戻してきたとき、依頼者に差し戻さず本体が方針を書いて次へ渡す | なし |
| 7 | 受付の質問を一度に | 残った疑問を 1 コメントにまとめて一度だけ聞き、残りは受付が決めて前提として記録する | `questions` / `question_max_items` / `question_max_rounds` / `question_deadline_weekdays` / `assumption_max_items` |
| 8 | 納品の深さを実行の中へ | 「どこまで届けるか」を最初の納品カードの前に 1 回決めて封じ、そこまで運んでから成功と呼ぶ。届かなかった差は最終コメントに 1 行で出る | 納品先の `delivery` / `chain.deliver.*` / `chain.deliver.go_gate` |
| 9 | 成果ベースの報告 | 最終コメントの先頭を「この依頼でできるようになったこと」にし、前提と裁定を読める場所に置く。出した後の確認まで本体がやる | なし |
| 10 | 本体に手段を渡す | 依頼を果たすのに要る鍵とアカウントを、名指しした工程のプロセスにだけ環境変数で渡す。値は記録にも画面にも出ない | `chain.credentials[]` |
| 11 | リリース経路が無い納品先 | 経路が無ければ「設定してください」と頼まず、本体が作れる部分を同じ Pull Request に入れて出す。deploy の workflow は、中身の決まりを渡された納品先でだけ本体が書く | `infrastructure` / `github_contract` / `chain.deliver.*` |
| 12 | 受付の判定役 | 受付が質問を残したとき、別の決定モデルに「このまま進めてよいか」を確かめ、確信度が足りて残った質問すべてに受付自身の提案既定があるときだけ、質問せずに前提として進む（任意の役。無ければ今までどおり。実測は次の 3 を参照） | `models.reception_judge` / `proceed_threshold` |

## 3. 残っていること

### 完成へ進める裁定と復旧

レビューの往復検知は、既存の裁定を呼ぶ条件の修正であり、納品の保証ではない。裁定役には現在の候補・指摘・依頼と、検査済みの過去の試行履歴を渡し、実際に渡した材料を裁定記録に残すようになった。チェーンからの引き渡し、実際の worker CLI の送信内容、壊れた記録・別依頼・履歴の上限・改変の検知は自動試験で確認する。**モデルがその材料から有効な代案を選んで納品できるかは実機で未検証。** 裁定役自身によるリポジトリ調査もまだ無い。指摘コード自体が毎回変わる往復は検知できない。期限・回数・内部エラーで終わる経路は残り、これらを失敗報告や同じ処理の無限反復ではなく、許可された範囲内での完成へ変えることが未達事項である。依頼の明示的な変更範囲を裁定役の「前提」で広げて達成扱いにはしない。

受付済み判定の破損は `internal/runner/reception_record.go` で保存済みの判定または検算済みの材料から復元する。カードを捨てたり受付へ戻したりはせず、最初のカード作成前の中断も同じ引き渡し処理で再開する。判定役の答え・設計要否の保持、異なる依頼や改変済み記録の拒否、繰り返す破損、復元待機中の停止を自動試験で確かめる。実機への反映と障害注入は未確認。復元材料そのものをすべて失った場合は保持して待つだけであり、完成へ至る自動復旧は引き続き未達。

### ダイジェストのコミットを作る段

`github_contract.staging_digest_commit` は「staging へ反映された内容を記録するコミットの形（メッセージの接頭辞・対象パス・実行者）」の申告で、本番への昇格はこの申告と実物のコミットを 1 文字ずつ突き合わせる。**いまはどの巡にもそのコミットを作れとは指示していない。**本体が観測できるのは反映されたパスだけで、接頭辞と実行者は観測できないため、この設定は本体が書かず「未適用」として名前で報告する（`internal/attendant/depth_gap.go`）。**作るところまでやらせるのは別の変更。**それまで、この申告を要する納品先は人が書く。

### 受付の判定役が決めた実例

2 段目（残った質問を判定役の確信度で前提に変える経路）は入ったが、既定の閾値 0.90 では、校正に使った 35 件の依頼のどれも変換されない（受付が実際に質問した 4 件を覆さない値として選んだ。表は [SETUP.md](SETUP.md)）。**判定役が質問を前提に変えた run は、まだ一度も無い。** 最初に役を有効にした納品先が最初の実測になる。変換が起きた run は `history/readiness/decision.json` に判定役の答えと確信度を残し、【実装方針】のコメントにその旨の 1 行が出る。

### 監査対応の後に残した 3 点

- **待機中の停止の読み取りに間引きが無い。** はしごが待機している工程は毎 pass (既定 10 秒) で課題のコメント一覧を読む (`internal/attendant/ladder.go`)。待機中の依頼 1 件あたり毎分 6 回、N 件なら 6N 回。claimed の run が使う 30 秒の記録 (`stop-read.json`) と同じ仕組みに載せれば、約束 (1 分以内) を保ったまま 3 分の 1 になる
- **役の持ち時間と card の壁を読み込み時に突き合わせていない。** 各 card は kanban に渡す持ち時間から 1 分手前で自分を止める。役の持ち時間 (`agents.<役>.timeout` 相当、上限 120 分) がそれを超える設定を書くと、その工程は構造上完走できず、時間切れとして数えられて終わる。同梱の設定とウィザードの既定は最小でも 9 分の余裕がある。読み込み時に拒否すれば、設定した人が最初に気づける
- **`internal/runner/stages.go` の `baseline` は殺された context を握り潰す。** attendant 内の `PrepareChainRun` から呼ばれる経路で card の壁の下には無いため、今日は到達しない

### 設計の巡の裁定

停滞の裁定が効くのは**実装の巡だけ**で、設計の巡には入っていない。設計の判定役が指摘を出し続ける依頼は記録の天井 50 巡まで回り、そこで `design_nonconverged` で終わる。入れるなら、停滞の判定条件を設計の巡の記録 (`history/design-N/decision.json`) にも広げ、同じ裁定役に「判定役を退ける」「設計役に何を満たすか指示する」を返させる形になる。

### 独立監査の指摘（対応済み）

2026-09-26 の独立監査（対象は 12 本目の 1 段前の main）が 10 件を出した。内容は妥当と判断し、4 本に分けて対応した。4 本とも main に入っている。

| 本 | 対象 | 中身 |
|---|---|---|
| A | はしごの終わり方 | 工程の時間切れを外からの中断と区別して再試行回数に算入する / はしごの待機中も停止を毎 tick 読む / **実行全体の期限 `run_deadline_hours`（既定 8）を設け、超えたら「ここまでやった」の最終報告で終える** |
| B | 停止 | claimed のどの段階でも、停止要求を 1 tick 以内に受け付けたと掲示し、実行中のカードを片付け、着地済みの状態を偽らずに終える |
| C | 最終報告の再送 | 終端を決めた時点で再送可能な報告そのもの（本文 + digest）を永続化し、盤面や成果物の再構築に依存せず同じ報告を再送する |
| D | 文書の契約 | README の巡の上限を実装に合わせる / 保証の始点と運用者が選んだ例外を明記 / `internal_failed` の残存条件を分類 / staging 止まりの最終コメントの矛盾を直す / このファイルを置く |

永久に直らない障害に当たった依頼も、実行全体の期限（`run_deadline_hours`、既定 8 時間）で「ここまでやった」の最終コメントに到達する。工程自身の時間切れは再試行回数に算入され、停止ははしごの待機中でも次の巡で効く。

## 4. 次に触る人が最初に確かめること

上から順に。下へ行くほど時間がかかる。

### ① 組み立つか・試験が通るか

```sh
go build ./... && go vet ./...
GOMAXPROCS=2 go test -p 1 -count=1 ./...
```

共有マシンでは `GOMAXPROCS` と `-p 1` を必ず付ける。全 package が `ok`（試験の無い package は `no test files`）になること。1 行でも `FAIL` があれば、そこから先は確かめる意味がない。

### ② 実行環境が動いているか

```sh
cd <消費側リポジトリの root> && lassdas run status --project <name>
cd <消費側リポジトリの root> && lassdas setup check --project <name>
```

（`cd` を省くと、別のディレクトリで実行したときに違う repo として扱われる。利用者に渡すコマンドは常にこの形にする。）

`run status` は本体が起きているか、`setup check` は設定と鍵の不足を示す。**check は鍵の値を表示しないし、聞きもしない。**どこで動かしているかは、導入した人が `.lassdas/progress.md` にそのまま打てるコマンドで書き残している。

### ③ 盤面が見えるか

盤面（board）は、いまどの依頼がどこまで進んでいるかを見る画面。出る port は設定の `board_port` で、公開範囲は導入のときに決めている。開き方も `.lassdas/progress.md` にある。**盤面が見えない状態で依頼の挙動を追うのは、記録を 1 件ずつ読むことになるので割に合わない。**

### ④ 依頼が通るか

```sh
cd <消費側リポジトリの root> && lassdas setup smoke --project <name>
```

1 ファイルに 1 行足すだけの小さな依頼を起票し、Pull Request ができるまで見届ける。**ここまで通って初めて「動いている」と言える。**組み立ちと試験は作る側の証拠であって、依頼が通る証拠ではない。

確かめる順を飛ばさないこと。②③ を飛ばして ④ をやると、落ちたときに設定と実装のどちらが原因か分からない。
