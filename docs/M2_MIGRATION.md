# M2 移行設計: 進行と実行の Hermes 純正化 (draft 2026-08-21)

対象: docs/TARGET_SHAPE.md (確定済みの最終形) への移行。本書はその実施設計 — 何を・どの順で・どこまでやったら完了か。

## 概要

現行 (M1) は「受付・進行・実行・関所」を全て自前 Go が駆動し、実行だけ claude/codex CLI を外部呼び出しする。M2 では**進行を Hermes 純正カンバンに、実行を Hermes 純正エージェントに移し、自前 Go は関所 (policy kernel) だけ残す**。ハーネスは 1 本になり、CLI 同梱・版追従・自前進行配線 (テスト 0% の 1,272 行) が消える。

## 背景と根拠 (要約)

- 維持/廃止評価 + 独立 2 系統クロスチェック (issue #9) の帰結: 実失敗 3 件 (606/608/610) は全て自前進行配線で発生。価値は関所に集中し、その関所はプロセス境界で既に分離済み
- 発注者決定 (2026-08-21): 道 2 直行 (現行形での受入再挑戦はしない) / 実行も Hermes 純正 (一番シンプルな形から始め、不足したら分離)
- 608 型の非収束 (毎巡新規指摘で上限到達) への本命対策 — Hermes 純正の巡別レンズ + 過去試行の受け渡し — は純正エージェント実行時にのみ働く (実測: direct-command では 5 設定が無視される)

## 設計

### 全体の骨格

```
attendant (常駐・自前)                Hermes (純正)                     kernel (自前 CLI)
──────────────────────               ─────────────────────────────    ─────────────────────
Backlog 監視 60s
 ├ 受付判定 (拒否既定) ──────────▶ 親カード作成 (--idempotency-key)
 ├ 質問投稿/回答取込 ◀──────────── needs_input ブロック/解除
 └ 終端報告投稿      ◀──────────── 親カード done/blocked
                                    実装カード (純正エージェント) ──▶ candidate 封緘 (worker seal)
                                    レビュー列 (純正 review lane,      ├ review 記録 (digest 束縛)
                                      レビュアー明示指定で 2 者交互) ──▶ ├ decide (拒否権)
                                    検証カード ─────────────────────▶ └ validation evidence
                                    納品カード ─────────────────────▶ controller publish
                                                                        (関所: 全再検算 → PR 作成)
```

- **契約の置き場 (最重要の設計判断)**: Hermes 側の進行は緩くてよい (レビュー素通り・手順逸脱が可能なまま)。**強制は納品の一点に集約する** — kernel の publish gate が「この candidate digest に対し、設定された 2 レビュアーの有効な記録 + converged 決定 + 検証証拠」を再検算し、揃わなければ PR は作られない。進行側の逸脱は「納品されない」という形で必ず表面化する (fail-safe 方向)。台帳外カードが 1 行で死ぬ現行原理の一般化
- **実行**: 実装役・レビュー役とも Hermes 純正エージェント。モデルはゲートウェイ経由で 2 系統 (実装+レビュー A = anthropic/claude-opus-5、レビュー B = openai/gpt-5.6-sol-pro — 現行と同一ペア)。ベンダー実体の突合 (自己申告ベンダー名と接続先の一致検査 + 実装役と同一 (baseURL,model) のレビュアー拒否) を kernel の設定検証に追加する
- **レビュー方式 (決定)**: 同一カードの純正 review lane を使い、レビュアーを毎回明示指定して 2 者を交互に通す (A 承認 → B レビュー → 両承認で次へ)。並列子カード方式 (P3) は不採用 — 純正 lane と排他であり、lane 側にだけ巡別レンズ・provenance・差し戻しの状態機械が揃っているため。逐次化のレイテンシ増は受入で実測し、問題なら P3 を再検討 (記録: TARGET_SHAPE の「不足したら分離」原則の適用対象)
- **質問**: kernel の質問プロトコル (2 回上限・記録連鎖・期限) は無変更。attendant が needs_input カードと Backlog 質問/回答を橋渡しする (回答採用 → `unblock --resolve` は実装済みの既存機構を流用)
- **レビュー容量問題 (610)**: 新形ではレビュー役がリポジトリを直接読むため、詰め込み上限は構造ごと消滅。chat レビュー経路 (`ReviewCandidate`/`reviewPrompt` 系) は Phase 3 で削除 (issue #13 はこの削除で closed)

### 実施フェーズ

**Phase 0 — kernel の下準備 (現行を壊さない)**
- worker verbs を Hermes ワーカーから呼ぶ前提の整理: 封緘/review 記録/decide/validation の各 verb が workspace 境界だけで動くことの確認とテスト追加 (現在 77-90% カバレッジの層。触るのは検証の追加のみ)
- 設定検証の強化: ベンダー実体突合 + 実装役と同一 (baseURL,model) のレビュアー拒否
- 非収束/機構失敗でも経過記録 (trail) を終端報告に載せる (issue #10 — 新形の失敗分析はこれが頼りになるため先行)

**Phase 1 — Hermes 側の組み立て**
- 実装/レビュー/検証それぞれの Hermes プロファイル + 手順書 (skill) 作成。手順書には kernel verb の呼び出し規約と巡別レンズ (純正 sdlc-review を土台に、kernel 記録の手順を追加) を書く
- attendant のカード作成を「親カード + 純正 lane 運転」型に変更 (idempotency-key は非 UNIQUE のため単一 attendant 前提を維持 — 実測済みの制約)
- 質問橋の接続変更 (needs_input ⇄ 既存質問プロトコル)

**Phase 2 — 受入 (最終形の上で初納品)**
- 同一の実チケット (組織別モデルホワイトリスト、裁定 4 件焼き込み済み) を新形で投入
- 安全性質の再実証 3 点: 台帳外カード遮断 / 3 回目の質問が物理的に不可能 / 起票者・カテゴリ外の拒否
- 成功 = PR 作成 + 関所ログで検算の成立を確認 → 発注者の合否判断

**Phase 3 — 切除 (受入合格後のみ)**
- `internal/runner` (1,272 行)・chat レビュー経路 (~260 行)・旧 GHA 構成 (Go 2,151 行相当 + YAML 2,198 行)・未使用 DynamoDB/Lambda 経路・claude/codex CLI の Dockerfile 同梱、を削除
- 削除は 1 塊ずつ PR 化し、都度 `go build/test` 全通過を確認

### 見積もり (実数・根拠付き)

| フェーズ | 新規/変更の規模 | 作業日数 (私の実働) |
|---|---|---|
| Phase 0 | テスト追加 + 設定検証 ~300 行 + trail 配線 ~50 行 | 1-2 日 |
| Phase 1 | プロファイル/手順書 (コード外) + attendant 変更 ~400 行 + 質問橋 ~200 行 | 3-5 日 |
| Phase 2 | コードなし (受入運転 + 計測) | 1-2 日/回 × 失敗回数 |
| Phase 3 | 削除 ~6,000 行 + ビルド検証 | 1-2 日 |

カレンダーでは 2-3 週間 (受入の失敗回数に依存)。Phase 1 の手順書設計が最大の不確実要素。

## 中止・分離条件 (事前確定)

- **実装役の分離**: 実装品質が原因の受入失敗が連続 2 回 → 実装役のみ claude CLI に分離 (TARGET_SHAPE の規定)
- **移行自体の中止**: Phase 1 で「2 者交互レビューを純正 lane で安全に表現できない」設計上の行き止まりが 3 営業日以内に解けない場合 → 発注者へ報告し、P3 (並列子カード) 案への切替か中止を諮る
- Phase 3 は受入合格まで着手しない (動く状態を壊してからの受入をしない)
