# LassDas 信用のしくみ — 登場人物と検算の全体図

LassDas の存在理由は 1 行で書ける。

> **AI がした仕事を、信用してよいか機械が判定できる形にする。**

本書は、それを「誰が」「どこで」「どうやって」実現しているかを、登場人物から順に説明する。実装の根拠は各所に `ファイル:行` で示す (branch `feat/hermes-runtime`, commit dcbf26b 時点)。

## 用語 2 つだけ

- **指紋** = SHA-256 ハッシュ。内容から計算される 64 文字で、内容が 1 文字でも変わると全く別の値になる。
- **確定記録** = 自分の指紋を内側に含めて保存される JSON ファイル。後から中身を書き換えると指紋の再計算が合わなくなるので、改変がその場で検出される。チケット・元ファイル・候補・レビュー・判定・検証結果は全部この形式。

## 登場人物

| 登場人物 | 正体 | 役目 | 信用するか |
|---|---|---|---|
| 発注者 | 人間 | チケットを書く。質問に答える。受け入れる | 唯一の最終権威 |
| 受付 | AI 2 人 (起案役+確認役、別会社) | チケットが自動処理に足るかを判定。許可した起票者・カテゴリ以外は受け付けない | しない |
| 実装役 | AI 1 人 | コードを書く | **しない** |
| レビュー役 A / B | AI 2 人 (別会社) | 変更を通すか判定。書き込みは許されない | **しない** |
| 質問の文案役 | AI 1 人 | 行き詰まった時だけ、発注者への質問を作る | しない |
| **関所** | **ただの Go プログラム (AI ではない)** | 上の AI 全員の仕事を検算し、そろわない限り PR を出さない | **ここだけ信用する** |
| 進行係 | Go プログラム (現 runner → Hermes に交代予定) | 各役を順番に呼ぶだけ | しなくてよい (下記) |
| Backlog 橋 | Go プログラム (attendant) | 受付結果・質問・完了報告をチケットに書く | — |
| 調査・設計役 | AI 1 人 (重いモデル)。**プロセスを持たない**: 関所がモデルを呼び、道具は `probe` 1 つ | 稼働環境とリポジトリを読み取り専用で計り、調査報告または設計書を書く ([INVESTIGATING_DESIGNER.md](INVESTIGATING_DESIGNER.md)) | **しない** |
| 写し役 | AI 1 人 (軽いモデル) | 設計書を写す。判断しない。設計書に無いファイルを触れば関所が止める | **しない** |
| 画面確認 (写真係) | Go プログラム (`browsercheck`) | 反映後の画面を開き、約束の文言を照合し、写真を残す | 関所の一部 |

核心はこの一点に尽きる:

> **信用するのは AI ではなく、AI を検算する決定論のプログラム (関所) だけ。** AI は全員「間違えるかもしれない・嘘をつくかもしれない」前提で扱う。だから進行係がどれだけ緩くても (Hermes に総取り替えしても)、納品物の品質保証は壊れない — 出口が関所の 1 本しかないからである。

## 1 チケットの一生

```
発注者がチケットを起票
  │ 受付: 許可起票者+カテゴリのみ通す (拒否既定) → AI 2 人が内容の充足を判定
  │ (内容が曖昧なら、ここで発注者に質問できる)
  ▼
実装役がコードを書く
  │ 関所が git で「実際に変わったファイル」を読み取り、候補の確定記録を自分で作る
  ▼
レビュー役 A と B が判定 (書き込み禁止・別会社・観点は別)
  │ 1 人でも差し戻し → 実装役がやり直し (最大 5 巡)
  │ 最終巡でも合意なし → 発注者に質問 (2 回まで) or 正直に失敗で終了
  ▼
テスト・lint (決定論検証 — AI 不使用)
  ▼
関所の納品ゲート: 全確定記録を再検算。そろわなければ PR は物理的に出ない
  ▼
GitHub PR (納品)
```

## 検算の中身 — 9 つの疑いと、その潰し方

「機械が判定できる」の実体は、次の 9 つの疑いを 1 つずつコードで潰していることである。

### 疑い 1: 実装 AI が「やりました」と嘘をつくかもしれない

実装役の自己申告は**採用しない**。実装役の実行が終わった後、関所が `git status --porcelain` で作業コピーを自分で観測し、実際に変わったファイルだけから候補の確定記録を組み立てる (`internal/worker/agent.go:209`、`cmd/worker/agent.go:99-114`)。書ける範囲の外に触れた形跡があれば、その時点で失敗になる。

### 疑い 2: レビューされた物と、納品される物が違うかもしれない

各レビューの確定記録には、判定対象だった**候補の指紋**が焼き込まれる (`internal/worker/artifact.go:96-116` の `candidate_sha256`)。納品ゲートは「この指紋の候補」に対するレビューしか数えない。指紋の違う候補にすり替えれば、レビューは全部無効になる。

### 疑い 3: レビュー AI が、こっそり自分で直してしまうかもしれない

レビュー役に書き込み許可はなく (`cmd/worker/agent.go:197-199`)、レビュー終了後に関所が**作業コピーと候補のバイト列一致**を照合する (`cmd/worker/agent.go:237` → `internal/worker/agent_review.go:41-45` `ConfirmTreeMatchesCandidate`)。1 バイトでも変わっていたらレビューごと拒否。「作者が自分を審判しない」と対になる「審判が作者にならない」の担保。

### 疑い 4: レビュー 2 人が同じ穴を見逃すかもしれない

レビュー役は**別会社のモデル 2 系統が必須** (`internal/worker/config.go:559-577`「reviewers must use at least two vendors」)。さらに各自に別の観点 (lens) を与える。判定は全員一致が条件で、**1 人でも差し戻しなら通らない** (拒否権 — `internal/worker/artifact.go:471-483`: verdict に 1 つでも revise があれば converged にならない)。受付側の 2 人 (起案役と確認役) も同じく別会社必須 (`config.go:591-592`)。

### 疑い 5: 昔の承認や、他の実行の承認を使い回すかもしれない

各レビューはレビュアー ID・モデル・接続先・モデル呼び出し ID・候補指紋で束縛され、判定の確定記録は「設定された全レビュアーが 1 人 1 回ずつ、この候補に対して」を検査する。レビュアー ID の重複も、モデル呼び出し ID の重複 (同じ応答の 2 回使い) も拒否される (`internal/worker/artifact.go:451-495`)。

### 疑い 6: テストは通ったが、別のコードで通ったのかもしれない

決定論検証は、資格情報を消した環境でテスト・lint を走らせ、**実行の前と後の 2 回**「作業コピー = 候補のバイト列」を照合する (`internal/worker/validation_evidence.go:44-118`)。テストが済んだ後にコードが変わっていれば失敗。使ったツールの版も観測して記録し、設定と照合する。結果は候補指紋入りの確定記録になる。

### 疑い 7: 何かが欠けたまま PR が出てしまうかもしれない

PR を作る経路は 1 本しかなく、その入口が納品ゲート `ValidatePublishGate` (`internal/worker/validation_evidence.go:161-180`)。「AI が合意した」だけでは不十分で、**同じ候補指紋を持つ決定論検証の証拠が揃わない限り通らない** (コード内の宣言: 「AI convergence alone is insufficient」)。しかも controller は PR 作成の直前、確定記録をファイルから読み直して**もう一度**このゲートを通す (`cmd/controller/commands.go:100`, `:610`)。

### 疑い 8: 検査の後、マージの瞬間にすり替わるかもしれない

マージ結果 (どのコミットがどこに入ったか) を API で取り直して照合する (`internal/githubapi/waits.go:459,485,503` `verifyMergeResult`)。検査時点と実際に入った物の食い違い (いわゆる TOCTOU) を潰す。

### 疑い 9: AI が勝手に仕様を決めて納品するかもしれない

発注者に質問を出せる場面は 2 つに限られる。①受付時、チケットの内容が実装を確定できないと判定された時。②最大巡数 (設定 1〜5、`config.go:408`) を使い切ってもレビューが合意しない時 — 逆に言えば、**合意に至った実行に質問を出すことはできない** (`internal/worker/impasse.go:69-72`)。レビュー役自身に質問経路は無く、迷ったら差し戻せと指示されている。質問は合計 **2 回まで** (`internal/hook/question_protocol.go:19` `MaxClarificationRounds = 2`)。回答は確定記録になって次の試行に束縛され、使い切ったら正直に失敗で終わる。

## 全体をつなぐ糸: 指紋の連鎖

各確定記録は「自分が何から作られたか」の指紋を内側に持つ:

```
チケット (input_sha256)
  └─ 元ファイル一式 (source_sha256 — base コミット SHA も含む)
       └─ 候補 (candidate_sha256)
            ├─ レビュー A (candidate_sha256 を内包)
            ├─ レビュー B (candidate_sha256 を内包)
            ├─ 判定 (review_sha256 ×2 を内包)
            └─ 決定論検証 (candidate_sha256 を内包)
                 └─ 納品ゲート: 上の全部を突合して PR へ
```

設定 (config_sha256) とエンジン自体の版 (tool_sha) も全記録に焼き込まれるので、「どの設定・どの版の関所で検算されたか」まで後から突合できる。どこか 1 箇所でも合わなければ、納品ゲートで連鎖ごと無効になる。実行の存在自体も台帳 (SQLite) が唯一の真実で、カンバンの盤面はその投影にすぎない (`internal/runtime/cards.go:140-144`)。

## 保証すること / 保証しないこと

**保証する:**

- 納品された PR の中身は、レビュー 2 者 (別会社) が見て承認し、決定論検証が通った、**まさにそのバイト列**である
- レビュー・検証の記録は後から取り替え・使い回しができない (取り替えた瞬間、指紋が合わなくなる)
- 質問なしで AI が仕様を勝手に確定して納品する経路は存在しない

**保証しない (正直な限界):**

- **暗号学的な否認不能ではない。** 指紋は鍵なしの SHA-256 なので、確定記録と関所のコードの両方を書き換えられる立場の者は偽造できる。守っているのは「関所を通る限り、検算なしの納品は不可能」まで。それ以上 (非対称署名・外部への記録固定) が要件になったら新規実装が必要
- **レビューの判断が正しいことは保証しない。** 保証は「そのレビューが、その内容に対して、独立した 2 系統で実際に行われた」こと。判断の質そのものは、別会社 2 系統・観点分離・決定論検証という緩和策で高める (保証と緩和策の区別は README と同じ)
- **ベンダー名は設定上の自己申告文字列**で、接続先との突合はまだ無い (既知の穴として記録済み。同一接続先のレビュアー 2 人を「別会社」と申告できてしまう)
- 関所自身は信用する前提。ここはテストと人間のレビューで守る層で、AI に書き換えさせない

## M2 (Hermes 移行) で何が変わるか

**退場するのは進行係 (runner) だけ。** 進行は Hermes カンバンに、実装役・レビュー役も Hermes エージェントに変わるが、「AI を信用しない」構造は不変 — レビューは関所が起動し (自己申告のレビュー持ち込み経路を作らない)、実装の成果は今と同じく git 観測で取り、関所の検算 9 点は全部そのまま残る。実装役とレビュー役が同じプログラム (hermes) になるため、審判の分離は「別プログラム」検査から「別プロファイル + 別資格情報 + 関所起動」に置き換える。詳細は `docs/M2_MIGRATION.md`、最終形は `docs/TARGET_SHAPE.md`。
