# CLI アプリを手元で立ち上げる

`lassdas init` は、接続先の設定から最初の依頼が PR になるまでを案内する。初版は Apple Silicon の Mac と Docker Desktop の Linux/arm64 が対象。本体は Pod と同じイメージを使う。

本書の実装と、実サービスを使った受入は別に確認する。新規 project・volume での PR 到達を 3 回連続で確かめる受入は [設計書 §10](INIT.md#10-段階導入と受入-dod) に従う。ローカルの試験だけではこの受入を完了したと扱わない。

## 準備する

Git、`go.mod` の指定を満たす Go、起動済みの Docker Desktop、既存の取り込み枝を持つ納品先の Git repo を用意する。納品先の検証コマンドは、実行イメージにある道具で通る必要がある。

イメージの配布者から、digest 固定の参照 (`registry.example.com/engine@sha256:…`)、対応するエンジンのソース SHA (40 桁)、両者の対応を確認できるビルド記録を受け取る。非公開イメージへの認証も外で済ませる。タグ名から対応を推定しない。

現在のイメージからソース SHA を復元する仕組みはない。また、init 用の `worker check-consumer`、`worker check-runtime` と、板の `LASSDAS_BOARD_AUTH=local` に対応するイメージが必要。古いイメージでは起動前検査が止まる。取得可能な参照は既存の配布者に確認する。

鍵も外で取得し、対話画面へ入力する。

| 用途 | 必要な権限と扱い |
|---|---|
| 納品先 GitHub | repo の読み取り、Contents と Pull requests の書き込み。read 成功だけでは write を確認済みにしない |
| トラッカーの自動処理 | 対象 project・利用者・課題の参照、運転用のコメントと状態の更新 |
| トラッカーの管理者 | 不足するカテゴリ・状態の作成を bot に許可していない場合に入力。作成限りで保存しない |
| 起票する本人 | 許可起票者 ID と一致する本人の鍵。最後の動作確認で入力し、保存しない |
| モデル | OpenRouter のキー、各役のモデル名・提供会社。既定はキー1本の共用、別キーは任意。疎通検査にも API の費用が発生する |

自動処理には起票者本人の Backlog キーも使える。同じアカウントの場合は、自動コメント・状態更新も本人名義になり、投稿者 ID では手動操作と区別できないことを確認してから進む。この用途で承認したキーは `runtime.env` (0600) に保存する。確認で中断したキーを新たに保存しない。再開時も名義を確認する。最後の動作確認だけに入力した本人のキーは保存しない。

初期版のモデル接続先は OpenRouter (`https://openrouter.ai/api/v1`) 固定で、URL の入力は不要。別の接続先で作った project の鍵を OpenRouter に転送しないため、その設定は自動変更せず新しい project を案内する。

既定は OpenRouter のキー1本を全役で共用する。キー単位の利用上限と費用は全役の合算になる。役ごとに分けたい場合は「役ごとに別の OpenRouter API キーを使いますか」で yes を選び、8 本の異なる鍵を用意する。受付の対象導出、受付の起案、受付の確認、実装、候補レビュー A/B、調査・設計、写し役である。役別キーを選び、設計レビューも別に指定する場合は A/B の 2 本も用意する。省略時は候補レビューと同じ役の鍵を使う。

## 起動する

エンジンのソースを取得して、そのディレクトリで実行ファイルをビルドする。

```sh
go build -o lassdas ./cmd/lassdas
```

納品先のローカル repo から呼び出す。`sample-cli` は保存先を区別する自分の project 名へ置き換える。

```sh
cd /path/to/consumer
/path/to/engine/lassdas init --project sample-cli
```

`--project` を省略すると保存名を聞く。別の作業場所からは `--repo-root /path/to/consumer` でも指定できる。旧 `setup.sh` は新しい init を呼ぶ互換入口で、旧 setup の台帳を新形式として取り込まない。

対話は次の順で進む。

1. GitHub の鍵、repo と取り込み枝、固定イメージとビルド記録を入力する。
2. 編集範囲、依存導入と検証のコマンドを確認する。確定した SHA の一時 clone を同じイメージ内で試走する。納品用の鍵は検証へ渡さない。
3. トラッカーの接続先、自動処理の鍵、許可起票者、カテゴリ・状態を確認する。不足項目の作成には内容の確認が入る。
4. モデルと共通キー（任意で役別キー）を入力し、すべての役の設定と疎通を確かめる。
5. 本体を起動し、設定・固定バイナリ・別ユーザでの起動・秘密の読み取り制限・板を認証なしで開けることを確かめる。
6. 本人の鍵を入力し、1 ファイルの小変更と PR の宛先を確認して起票する。設計・レビュー・写し役・検証の記録と、実在する PR の差分を照合する。

編集範囲の `main.go` はそのファイルとの完全一致、`src/` はそのディレクトリ内を意味する。ワイルドカード・隠しファイル・シンボリックリンクを編集範囲に含めない。CLI の出口は PR で、デプロイ URL や release 枝は設定しない。

道具はイメージにある版で確かめる。ホストにしかない道具では通らない。検証時の環境変数は絞られるが、検証コマンドは通常の子プロセスである。分離の範囲と残るリスクは [設計書 §6](INIT.md) を参照。

## 中断から再開する

同じ `init --project sample-cli` で保存した回答と課題を引き継ぐ。特定の段から入力を見直す場合は `--redo` を使う。

```sh
/path/to/engine/lassdas init --project sample-cli --redo models
```

段の名前は `prepare`、`consumer`、`tracker`、`models`、`runtime`、`smoke`。redo でも課題と相関 ID を引き継ぐ。起票時に通信が切れた場合は、作成結果を照合するまで同じ依頼を再送しない。

動作確認の待機は既定で 30 分。超過時は進行中として表示を返し、init は未完了のまま本体が続く。同じコマンドで同じ課題を追跡する。質問にはその課題で回答し、失敗や予算不足は表示された工程と対処を確認する。

```sh
/path/to/engine/lassdas run status --project sample-cli
/path/to/engine/lassdas run logs --project sample-cli
/path/to/engine/lassdas run stop --project sample-cli
/path/to/engine/lassdas run start --project sample-cli
```

`stop` はこの project のコンテナを止め、台帳と作業記録を保持する。同じ設定での再開は、実行中の本体を停止しない。設定や鍵を変える場合は対象を停止してから適用する。

## 保存先と完了の意味

ホストの `~/.lassdas/<project>/` は 0700。回答と検査記録は `init.json`、運転用の鍵は `runtime.env` (0600) に保存する。本人・管理者の一時鍵はどちらにも保存しない。生成した `config/` だけを読み取り専用でコンテナへ渡し、実行台帳と作業場所は project 専用の Docker volume に置く。

板はホストの `127.0.0.1` に公開され、Basic 認証なしで閲覧できる。パスワードの取得や入力は不要で、起動時に表示する URL を開く。ローカルの板から回答・Go・停止の投稿は行わず、質問への回答は元の課題で行う。Docker を操作できるホスト利用者はコンテナの鍵も読めるため、状態ディレクトリと Docker の操作権限を共有しない。

本体の起動成功だけでは init は完了しない。起票した課題と PR の repo・取り込み枝・head・期待差分が一致し、設計レビュー、候補レビュー、検証、写し役の確定記録が揃って完了となる。別ユーザで動けることは起動時の検査で確認するが、個々の写し役記録に実効 UID が記録されるとは扱わない。
