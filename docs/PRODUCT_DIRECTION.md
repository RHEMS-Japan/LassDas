# LassDas の全体方針

2026-09-11〜13 の対話で合意した、製品と設計の方針。本書は今後の判断基準を定める。実装済みの機能や動作保証を示すものではない。

## 1. 本質的な価値

**利用者が、自分のプロジェクトに合う AI との開発ワークフローを構築し、実際に仕事を任せられるようにする。既存の進め方があれば取り込み、なければ LLM と相談しながら作る。**

人と AI が開発を進めるには、目的、作業の範囲、手順、確認方法、完了条件、人が判断する場面を共有する必要がある。その共通認識と実行環境を、利用者が毎回すべて手作業で組み立てる負担を減らす。

実績あるワークフローやテンプレートは任意の出発点として使える。既存の手順が一部だけある場合にも、不足を対話で補える。実績や完成済みの手順を、導入の前提にはしない。

プロジェクトごとの違いを扱う。たとえば Web アプリでは作業ブランチから統合先への PR、マージ、検証環境への反映、ブラウザでの確認が必要になる場合がある。CLI アプリではコマンドの出力、終了コード、生成物による確認が適切な場合がある。納品先や完了地点は、そのプロジェクトと依頼に合わせて合意する。

## 2. init は共通認識と実行環境を整える入口

`init` は、プロジェクトの開発ワークフローを対話で設計・構築・検証し、実行担当へ引き渡す「ワークフロー構築エージェント」の役を担う。プロジェクトを調べ、必要なことを利用者と相談しながら構築する。決めるべき事項を把握し、具体的な質問とその順序は、既存資料と対話に応じて組み立てる。選択式の入力や通常のフォームも、適した場面で使う。

手順やテンプレートは、init がリポジトリ、既存資料、CI や設定を調べ、プロジェクトに合う推奨案を理由とともに提示する。既存の手順がなければ利用者の希望を聞いて候補を出し、一部だけあれば不足を補う。利用者が必要な部分を修正して合意する。テンプレートは進め方を作る出発点として使い、合意を後述の `.lassdas/` へ保存する。

初期設計では、依頼ごとに担当する仕事の骨格を、指定先への PR の提出、合意した内容とタイミングでの検証、条件に応じたマージとする。init はプロジェクトの手順と利用者が任せたい範囲を調べて相談し、PR 先、検証方法・対象・合格条件・タイミング、マージ可否と条件、完了地点を具体化して `.lassdas/` に保存する。ブランチ名だけで用途を推測せず、既存の文書・設定・履歴から確かめる。

初期対応には、人が PR をレビューしてマージし、その後の検証を LassDas が担当する組み合わせを含める。LassDas は自動マージせず、対象の変更が指定先へ取り込まれたことと、検証に必要な反映を確かめ、合意した方法で検証して結果を報告する。マージの許可と、マージ後の検証を任せることを分け、この場合は PR の提出やマージだけで担当完了としない。検証対象・合格条件に照らして完了を判定し、未確認や失敗を成功として扱わない。人の判断を待つ期限は、関連する残論点として別途決める。

PR 提出後にレビュー指摘を受けた場合は、その内容を確かめる。元の依頼を満たすための修正なら、同じ依頼・同じ PR で修正し、再検証と必要なレビューまで担当する。追加機能や目的の変更なら、対応範囲を確認する。指摘を受けたことだけを理由に作業範囲を広げず、既に合意したマージの担当と許可条件も維持する。対応の期限・費用・回数上限は別途決める。

マージ後の検証で不具合が見つかった場合は、まず原因を調べる。元の依頼の範囲で必要な修正は、同じ依頼で修正 PR を作り、必要な検証・レビューを行う。修正 PR のマージも元の設定に従い、人がマージする設定なら人の判断を待つ。変更の取り消しや範囲外の対応が必要な場合は、影響と具体案を示して判断を求める。

依頼 1 件の納品と、複数の変更をまとめるリリースを分ける。たとえば stg への取り込みと指定の検証までを任せた場合、そこまでで依頼を完了とする。その後の stg 全体から prod への反映は、プロジェクトのリリース手順で扱う。依頼の完了条件に含まれない本番反映を、未完了の工程として抱え続けない。ブランチ名は例であり、固定値にしない。

初期の課題管理連携は Backlog と GitHub Issues を対象とする。Jira Cloud は後続の候補とし、初期対応の必須条件には含めない。その他の連携先やテンプレートの具体的な範囲は、[issue #167](https://github.com/RHEMS-Japan/LassDas/issues/167) で引き続き決める。

初期の外部サービスとのやり取りは、起票元の同じチケットで質問・回答・結果報告まで完結させる。Backlog の依頼は同じ Backlog のチケット、GitHub Issues の依頼は同じ Issue を使う。Slack・Telegram などとの追加連携は後続候補とする。

入口には、`lassdas init` が用意するハーネスと、利用者がすでに使っているエージェントへソース・セットアップ手順を渡す方法の両方を想定する。セットアップの知識・道具・検査を共通に利用できるようにする。init 担当の責務、決める事項、調査・質問・構築・検証で果たすべきことは、LassDas 本体のリポジトリに共通の指示として記載する。どの LLM や入口を使う場合も、その指示を参照してセットアップする。

最初は、利用者が開発用 AI と、ファイル操作やコマンド実行を行えるハーネスを既に使っている前提にする。その既存エージェントから共通の導入手順・道具・検査を使い、導入と試験依頼の確認まで進められることを先に実証する。その共通部分を専用の `lassdas init` エージェントからも使う入口の整備は後続とする。この前提は導入を担当する AI とハーネスについてのものであり、導入後の依頼受付・開発は本体へ引き継ぐ。

導入を案内するエージェントの担当はセットアップまでとし、その後の依頼受付と開発は LassDas 本体が引き継ぐ。セットアップでは、本体の各役割に使う LLM も利用者が選び、確定する。init が品質や費用の希望を聞き、役割ごとの推奨構成を理由とともに提示する。利用者は必要に応じて変更して確定できる。具体的なモデルや既定の組み合わせは、本方針では固定しない。

**init 自身による納品先リポジトリへの書き込みは、`.lassdas/` に限定する。** 既存の文書・コード・CI 設定は調査のために読む。合意・設定・参照先・進捗を `.lassdas/` に保存する。既存ファイルの修正が必要なら、理由と変更案を示し、別の開発作業として扱う。ワークフローを構築する責務と、そのワークフローでプロジェクトを変更する責務を分ける。

導入の流れは次を基本とし、不足や検証結果に応じて戻る。

1. リポジトリ、文書、既存の CI や開発手順を調べる。
2. 調べて分かることを埋め、利用者の意図や判断が必要な部分を質問する。
3. 作業の進め方、完了地点、自動で進める範囲、人に判断を戻す場面を示して合意する。
4. 合意を指示・設定・参照先として保存し、必要な実行環境を整える。
5. 接続や確認手順を試し、小さな試験依頼を実際に 1 本流す。そのプロジェクトで合意した納品と確認まで通ったことを確かめ、init 完了とする。

初回の試験依頼は、init がプロジェクトを調べ、合意した納品・確認まで通せる小さな変更を提案する。利用者が採用・変更を選ぶ。たとえば Web アプリで stg への反映とブラウザ確認まで合意しているなら、その経路を実際に通せる小さな画面変更を提案する。試験でプロジェクトを変更するのは、構築した実行側の担当とする。init は、その試験が合意した納品・確認まで通ることを確かめる。

導入時に予定した全工程を試せない場合は、確認済みの範囲を利用者と合意し、その範囲に限定して使い始められるようにする。たとえば「stg まで利用可能・本番は未検証」と明示し、自動処理も stg までに限定する。本番までの導入完了にはしない。未検証の工程と再開に必要な情報を進捗として残す。

試験に失敗した場合は、init が原因を調べ、合意した範囲内の `.lassdas/` の修正と再確認を行う。既存のコード・文書・CI 設定の修正が必要な場合は、理由と変更案を示し、別の開発作業として扱う。利用者の判断や操作が必要な場合は、その理由、現在地、具体的な操作、操作後の再開方法を示す。

質問は原則として答えやすい選択肢を出す。必要な選択肢や聞き方を LLM が考える。すでに読める情報を聞き直したり、通常の作業ごとに承認を取り直したりしない。外部サービスの鍵は取得方法を案内し、利用者が外で取得して安全な入力経路へ渡す。

合意した導入に必要な準備と変更案は init が示す。納品先リポジトリの既存 CI 設定の変更は、他の既存ファイルと同じく別の開発作業として扱う。外部の実行環境やクラウド権限の変更には、変更内容と影響を説明し、利用者からその変更への個別の承認を得たうえで実施・検証する従来の規則を適用する。導入方針への合意と、具体的な基盤・権限変更への承認を区別する。

## 3. 決める事項と、プロジェクトに委ねる内容

導入から利用終了までの具体的な論点、合意状況、残る判断、必要な設計・実装と受入は [INIT_DECISIONS.md](INIT_DECISIONS.md) に集約する。初期の提供範囲を決めることと、導入先ごとの設定値を決めることを分け、一覧全体を固定の質問票や必須機能にしない。

| 決める事項 | プロジェクトに合わせて調べ、相談する内容 |
|---|---|
| 依頼の入口 | どこから依頼を受け取り、誰の依頼や回答を扱うか |
| 作業の範囲と根拠 | 対象、参照する知識、触ってよい範囲、守るべき制約 |
| 開発と納品の進め方 | 作業の開始点、既存の手順、納品先、どこまで進めるか |
| 確認方法と完了条件 | 何をどこで確かめるか、成功・未確認・未達をどう区別するか |
| 自律性と人の判断 | 自動で進められる範囲、必要な判断、その判断をする人 |
| 進められない場合の対応 | 誰が何を確認し、利用者に何を伝え、どう再開・終了するか |
| 実行に必要な準備 | 接続先、道具、資格情報、実行環境、利用上限 |

これは固定の質問票ではない。該当しない事項は、その理由を含めて整理する。プロジェクト共通の運用は init で整え、個々の依頼の目的や受入条件は依頼から読み、不足があればその都度聞く。将来の全依頼を事前登録させない。

## 4. LLM・コード・人の役割

**LLM は、資料と状況を理解し、質問、提案、作業の組み立て、調査、実装、検証、修正を担う。** 合意した目的と制約の中で、次に必要な行動を判断する。全プロジェクトの手順や質問を、事前に条件分岐として列挙しない。

検証についても、init は各役がどう振る舞うか、何を満たせば合格かを相談し、`.lassdas/` に指示と参照を残す。実行側は既存のテストや CI を利用し、依頼に必要なテストがなければ、合意した作業範囲内で作成・実行し、必要な変更を成果物に含める。検証内容の違いを、その都度 LassDas 本体への専用機能追加として扱わない。init に将来の全テストや検証手順の事前作成を要求しない。検証対象は、PR 元やマージ後など、どの状態のコード・環境かも方法・タイミング・合格条件と合わせて具体化する。テストの内容も通常のレビュー対象とし、実行結果と対象の変更を対応付けて確認する。

初期に選べる検証対象には、PR 元の状態、実際のマージ後の状態に加えて、実マージ前に最新のマージ先と PR の変更を合わせた状態も含める。プロジェクトに応じて必要な対象とタイミングを合意する。組み合わせの検証では、その時点の PR 元・マージ先の変更と結果を対応付け、マージ先の枝を変更する実際の取り込みとは区別する。検証後に対象が変わった場合は、古い成功結果をそのまま流用しない。

保存するものには、設定値に加えて、仕事の進め方や判断基準を含める。すべてを固定の分岐や専用の記述言語に変換することを前提にしない。リポジトリ内の既存文書は在り処を参照し、手順の全文を別途複製して管理しない。対話で新しく決めた合意・設定と既存文書への参照を、後の実行でも使える場所へ残す。init が調査中に既存資料と実際の運用の食い違いを見つけた場合は、設定や変更履歴を調べる。それでも判断できなければ、相違点と根拠のある推奨案を示して利用者に確認し、確定した進め方を `.lassdas/` に保存する。元の文書にも修正が必要な場合は、その理由と変更案を示す。元の文書への反映は、そのリポジトリの通常のレビュー手順を使う別の開発作業として扱い、init 自身は変更しない。

共有するセットアップ結果は、納品先リポジトリの `.lassdas/` へ保存する。別の人やエージェントがリポジトリを読んで引き継げるようにする。ファイル形式の詳細は実装時に決める。資格情報の値は共有する成果物に含めず、従来のリポジトリ外の保存先から参照する。導入後の各役は、プロジェクト固有の進め方を知る入口として `.lassdas/` の合意・設定・確認条件を読み、必要な既存文書は記された参照先をたどる。LassDas 本体にある各役の共通指示と合わせて参照し、担当する AI が替わっても同じ前提で作業できるようにする。必要な内容を実行時に渡す具体的な方法と、その動作の確認方法は後続の設計で決める。

init の進捗も同じ `.lassdas/` に保存する。合意した内容、済んだ作業と成果物への参照、未解決事項、次の操作を残す。会話や端末を閉じても、再開するエージェントがこの記録を読み、既存の設定や PR などの実際の状態を確かめながら続きを進められるようにする。

通常のワークフロー変更は新しい依頼から適用し、実行中の依頼は開始時に合意した条件で完了させる。実行中の依頼にも適用したい場合は、その依頼について変更を合意する。プロジェクト共通の設定を更新しただけで、実行中の依頼の納品先や完了条件を切り替えない。

**コードとゲートは、機械で検査できる条件を執行する。** 権限、対象範囲、必要な承認、検査結果、検査した成果物と納品物の一致などを確かめる。LLM の説明だけで合格にせず、独立したレビューや実際の材料・動作と突き合わせる。ゲートが確認できる範囲も明示し、通過を未知の品質まで保証するものにしない。

**人は、目的、意図、任せる範囲、事前に合意した重要な判断を担う。** 判断を求めるときは、必要な材料と選択肢、その結果を示す。合意した範囲を越える操作は、通常の自律実行に混ぜない。

質問が柔軟でも、実行側が未知の手段をすべて扱えるとは限らない。合意した手順を実際に実行・検証できるか確かめ、未対応の部分は具体的に示す。設定を書き出しただけで、導入が完了したことにしない。

## 5. 利用者に見える運用もワークフローに含める

各状態から、何が済み、何が未確認で、次に誰が何をするかが分かるようにする。利用者の操作が不要なら明示し、必要なら確認対象、判断内容、操作手段、操作後の結果を示す。

機械が調べられる事実は先に調べる。「確認してください」だけで内部状態の解釈を利用者へ委ねない。例外対応を人が担う場合は、認証エラーなど発生した問題、現在地、対処・再開方法を共有し、対応する権限を持つ人がその情報から引き継げるようにする。導入した利用者など特定の個人を、既定の復旧窓口として固定する前提は置かない。投稿の成功、担当者の受理、対応の開始、復旧の完了は区別して伝える。

合意した成果物と確認が揃えば完了にする。必要な検査が未完了なら、その不足を示す。不要な工程が実行されないことを、根拠なく障害と扱わない。人による確認待ちの終了操作と、デプロイや自動復旧も区別する。

停止・確認済み・完了への移動には、理由と行われた操作を残す。利用者が、状態が変わった理由を追えるようにする。

## 6. この価値を確かめる方法

既存の運用を取り込む導入と、未確立の運用を対話で作る導入の両方を確かめる。性質の異なる実プロジェクトで、この導入機構を作った人以外の利用者が導入し、依頼し、適切な確認と合意した納品まで進められるかを見る。

導入時の変更を確認し、init 自身による納品先リポジトリへの書き込みが `.lassdas/` に限定されていることを確かめる。試験依頼を実行側が処理して作った変更と、init の変更を区別して確認する。

実行側が、保存された検証の指示に基づき、その依頼に必要なテストの作成・実行まで行える例も確かめる。init が直接プロジェクトのテストを書いた結果と混同せず、テスト内容・実行結果・対象の変更を確認する。

成果物の品質に加え、導入に必要だった手作業、質問、時間、費用、利用者の介入、失敗時の理解と再開を記録する。PR の作成や独立レビュー通過は重要な検査であり、導入と運用の使いやすさも別に確かめる。

## 7. 実装を進める際の判断

実プロジェクトで導入・運用して、不足と共通部分を確かめながら整える。将来あり得る全ワークフローへの対応を先回りして作らない。必要な設計・実装は行い、過剰な抽象化や仕組みの追加を避ける。

未対応によって導入が進まなかった場合も、その需要を LassDas 側へ届けられるようにする。init が実現したいことと調査で確認した不足機能を要望案にまとめ、利用者が公開する内容を確認して送信するかを選ぶ。送信先には LassDas の既存の GitHub Issues を使い、追加対応の判断材料にする。要望の提出と、開発への採用や提供時期の確約は区別する。

利用者による本体の追加開発は任意とし、導入の前提や利用者の必須作業にはしない。追加開発を選ばない場合も、未対応箇所と進捗を残し、要望の提出を選べるようにする。希望した場合の開発支援の具体的な手順は、別途設計する。

LassDas 本体の開発・リリースでは、既存の設定や保存された合意を引き続き扱える後方互換性の維持を基本方針とする。やむを得ず移行が必要な変更を行う場合は、init が影響と修正案を示し、利用者の確認を経て `.lassdas/` の更新と必要な再確認を支援する。これは本体の開発・リリース方針であり、プロジェクトごとの版固定を init の必須条件にするものではない。

既存の実装と未反映の変更も、本方針に照らして必要性を見直す。既存の開発・リリース経路を使い、共有基盤や権限の拡張を導入作業の既定にしない。

init エージェントの具体的な構成、保存形式、既存実装からの移行手順は、実例と検証結果に基づく後続の設計で決める。本書を理由に、未検証の構成を実装済みと扱ったり、停止中の作業を自動的に再開したりしない。

個別の設計議論は [全体 issue #160](https://github.com/RHEMS-Japan/LassDas/issues/160) からたどる。一問一答で進め、決定と残る疑問を対応する issue に記録する。 議論では目指す挙動を先に決め、決定ごとに必要な実装と受入条件を対応付ける。現行実装との差は実装課題として残し、設計上の合意・実装済み・検証済みを区別する。
